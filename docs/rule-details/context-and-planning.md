# 上下文与方案设计细则

来源：全局 `CLAUDE.md` §1.4 与 §2.4（2026-09-19 结构搬移，内容未改）。

## 方案设计

- 在设计任何方案的时候，都必须充分考虑、一步到位，不允许使用"第一版先怎么样，然后观察xx后再怎么样"的措辞；
- 不允许把方案分成稳妥和激进，如果在某些特殊场景下，你需要提出多个方案的话（实际上绝大多数时候你只需要提出一个方案，不要无脑做这件事），也需要是多个方案都成立的、平行的，而不是对于任何问题你都无脑地提出从稳妥到激进的多个方案。这没有任何的意义，一个稳妥但是不work的方案是没有任何价值的废纸。

## 搜索内容

- 如果我让你搜索A相关内容，你搜索到B、C、D发现不满足要求，就不允许再把B、C、D列举出来了。我根本就不关心，看到这些只会污染我的眼睛。

## 上下文与 Token 管理

- 开工即明确目标、成功标准、允许修改范围和验证方式；已有上下文足够时不重复询问。
- 上下文拉长后模型判断力下降，堆积到约十万 token（当前模型标尺，随模型迭代上移，作信号而非硬阈值）后明显变笨，与窗口容量无关。长任务主动切段并把接续状态落盘到文件，到段落边界时提示用户开新会话承接，不靠对话历史续接；同一件事未做完不建议重开，换不相干任务时建议清空重开而非压缩续聊。
- 调用工具或子代理时给明目标、约束、输入和验收标准，要结论、修改范围和验证结果，不要完整文件回显；简单定位和机械任务不用强模型或子代理，强模型留给架构、安全和复杂调试。
- 构造工具或子代理输入时稳定规则和约束放前部、动态报错/diff/测试输出放后部，保持缓存复用。
- 临时任务状态不写入全局 `CLAUDE.md`；需要持久化时根据授权写入项目文件或 auto-memory。每完成一个阶段保留简短状态（已确认/已修改/未完成/下一步/验证结果），复用不回放。
