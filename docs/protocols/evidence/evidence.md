# 证据与交付协议

管结论要用什么证据、验证做到哪一步、交付时给什么。

正文原本在 `~/.claude/CLAUDE.md` §3、§4，2026-09-25 原文搬入；常驻区只留索引行。

## 证据与来源

- 先给结论，再给关键依据；只输出必要且可审计的假设、证据、排除依据、风险和验证结果，不展开内部隐藏推理。
- 唯一且可证伪的事实问题，先查证据再回答。
- 平台能力与门禁类结论（工具是否支持某开关、命令的发现规则、schema）验收时当场实跑复测，不复述记录里的报错原文；CLI 静默自动更新会让数小时前的证据失效，先 `claude --version` 对版本再跑原命令。结论过期时同步修正所有引用处，不只改一处。
- 证据优先级：源码 > 官方文档 > 实测输出；第三方文章只作线索，决定性依据取三者之一。
- 记忆默认不可信；引用记忆中的文件、函数、配置或行为前先核对当前状态。无法核实时标明“**不确定**”及缺失证据。
- 未证实的假设同时说明风险与影响；用户质疑事实判断时，补充更强证据或承认不确定。
- 用户指定本地材料时只使用本地材料；来源不明先询问；涉及外部材料时先完整读取，再执行后续操作。
- 纯建议、风格选择和开放讨论可以直接基于判断，不套用事实核验门槛。

## 完整性

- 交付内容必须完整可运行；禁止占位符、假实现、用骨架冒充完整实现或用省略语掩盖未完成部分。
- 注释只记录代码无法表达的原因、约束或取舍。

## 改后检查

- 基于真实输出验证编译、测试、脚本或页面操作；没有可执行验证时明确标记待验证。
- 核对修改范围、权限、数据流和业务闭环；Bug 修复必须确认根因。
- Git 项目交付前运行：
  - `git status --short`
  - `git diff --stat`
  - `git diff --cached --stat`
  - `git diff --check`
- 提交前确认 `git status --short` 的**第一列**（暂存区）没有与自己无关的条目；有就用 `git commit -m <消息> -- <自己的路径>` 限定路径提交，保留他人已暂存内容。误提交后 `git reset --soft HEAD~1` 回到提交前的索引（`--soft` 不丢他人已暂存内容），再按 pathspec 重新提交。
- 迁移、恢复、配置对齐类任务（hook、MCP、插件、settings）的完成判定走三层，全过才算完成：① dump 运行时实际配置，不信计划文件里的「已完成」；② 脚本喂 payload 实测契约；③ 重启会话后跑触发清单验真生效。脚本改对 ≠ 接对 ≠ 真生效。
- 非 Git 项目检查文件清单与差异。
- 交付结论遵循本文件「证据与来源」一节的标准，并写明剩余风险和产物去向。

## 校验

`—`，暂无可机械校验的脚本：判的是结论背后的证据强度，不是磁盘上的固定形态。同批产物的形态检查（体积、重复、密钥）在 `python ~/.claude/hooks/scripts/protocol_check.py`。
