# Runtime and failure handling

## Runtime evidence

- 用户明确指定模型或 effort 时，先确认宿主支持，再按指定值调用；不预设指定模型必须属于某个供应商或模型系列。
- 用户未指定时，按任务难度和风险选择当前运行时实际可用的 worker 路由；低风险边界清楚任务优先较低 effort，复杂跨文件或高风险任务再提升。任意实际暴露的模型均可使用。
- 宿主不支持覆盖时，使用已验证的默认路由。无法确认模型、effort、并发或隔离能力时写 `unverified`，不得猜测或静默降级。
- 不修改主会话模型，不设置全局 worker 默认值，不创建供应商专属配置来伪造通用能力。

## Configuration review

每次启动子代理前，必须先向用户明确展示拟用配置：模型（可见时写实际名称，否则写 `unverified`）、供应商、路由、effort、并发数和隔离方式；同时判断配置是否合理，说明依据、影响和可选方案。随后询问用户是否采用；收到确认前不得启动 worker——**常规单个委派不豁免这道确认**。用户已经确认同一配置时不重复询问；不依赖配置回答的分析可以继续。

配置审查不绑定任何模型或供应商。没有可选配置、仅使用已确认的宿主默认值时，不为普通可逆执行增加审批；最终仍需报告实际使用值，无法确认则标记 `unverified`。

## Failure and downgrade

- 边界不清：缩小任务或留在主代理，不盲目派发。
- 存在顺序依赖：改为阶段式调度，后一阶段等待前一阶段验收。
- 写入冲突：拆分范围、启用隔离或顺序执行。
- 并行启动失败：不要伪造并行结果；改为顺序执行，或报告阻塞。
- 模型覆盖不支持：保留任务契约，使用已验证默认路由；无法验证时报告实际限制。
- 部分 worker 失败：保留成功结果，但不宣布总任务完成；处理失败项并完成整体检查。
- 结果越界、缺少证据或不满足验收：拒绝结果，必要时缩小范围后重新派发。

失败重派只能针对具体阻塞原因，不能靠增加并发、降低门禁或隐瞒失败来制造完成状态。
