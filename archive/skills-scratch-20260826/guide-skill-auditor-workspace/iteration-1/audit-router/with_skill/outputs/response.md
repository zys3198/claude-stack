## 将执行的检查框架（对 `ai-coding-guide`）

### 第 0 步 定靶
读 `SKILL.md` 全文 + description；列出声明的域（编码）及兄弟域（writing / learning / frontend 等跨域撞词面）。

### 第 1 步 静态十查（逐条 PASS/FAIL + 位置）
1. **description 定位**：what（「编码域开工路由器」类角色声明）+ when（触发词），且无流程摘要——漏写流程则 agent 照 description 执行不读正文
2. **版本戳**：`<!-- vX.Y.Z -->` 在 description 末尾，正文末门禁注释两处一致
3. **「不用于」清单 + description 路由目标列表无范畴词**：「其他/等/任何」类词 = FAIL（#1301 范畴词被放大解释）
4. **触发门禁**：正文有显式 3 行输出模板——相关性 YES/NO + 目标存在性 + fallback，位于分类/委派之前
5. **路由表兜底行 + 撞词行内联负向**：每行具体信号→具体路径；「其他」类兜底须给具体反问模板；与兄弟域共享触发词的行须行内写「何时不选它」
6. **路由目标合法性**：ⓐ 存在性（当前会话 available skills → 磁盘三处；查不到=幻觉，磁盘有但会话未装=待验证不算 FAIL）ⓑ 可直达性（自声明「被 X 引用」的参考层不得作路由终点）ⓒ 归属错位（项目约定/机械约束类目标应挪 CLAUDE.md 或 hook）
7. **默认值先于菜单**：意图明确直接给默认路径；菜单合理时每支写成可判定问句，空泛「你想要哪种」= FAIL
8. **路由表门禁**：文末 HTML 注释声明增删条目须引用真实证据
9. **配套文件**：`test-prompts.json`、`CHANGELOG.md` 必有；`references/MAINTENANCE.md` 推荐
10. **枚举信号表 + 缺口清单**：①明确信号→路径枚举表（命中即直跳不采访）②不命中/多解时按决策点逐点问的缺口清单；两张表皆无 = FAIL

### 第 2 步 动态基线（必跑判断）
审查「路由质量」触及 description / 域边界 / 路由表现状 → **必跑**，不以静态结果豁免。造 3-5 个边界场景 prompt，派子代理裸跑（只给 description 不给正文）看第一跳：
- 兄弟域边界信号（「帮我写篇文章讲我的项目」「这个页面布局」等撞词场景）
- 模糊信号（「帮我看看这个代码」歧义分拣）
- 点名下游 skill 的场景（第一跳进对域但目标是否存在）
- 降级到 fallback 场景（三域均不命中）

子代理连挂 2 次 → 主会话人肉走查并标注。每个边界 bug 修复后补镜像 test-prompt（本 guide + 兄弟 guide 各一）。
