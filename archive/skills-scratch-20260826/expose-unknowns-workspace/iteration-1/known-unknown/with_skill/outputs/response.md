## 判级：已知的未知

你已经明确了问题和两个候选方案，但还缺少会改变结论的约束；不是“未知的未知”，因为关键判断维度可以直接列出来。

## 双向钢人检查

### 最强支持 Caffeine

- 单体或单实例部署时，读取延迟最低、实现最简单。
- 不引入网络依赖和 Redis 运维成本。
- 适合热点订单查询、允许短时间旧数据的场景。
- 应用内缓存失效和容量控制更直观。

### 最强支持 Redis

- 多实例部署时所有实例共享缓存，避免每台机器重复占内存。
- 滚动发布、扩容后缓存仍然共享。
- 其他服务也需要读取订单缓存，或需要共享 TTL、失效通知时更合适。
- 如果所谓“缓存”还承担幂等键、分布式计数或跨实例协调，Caffeine 不能胜任。

### 决定性变量

最关键的不是订单模块，而是：

1. **是否多实例部署**
2. **缓存的是订单详情、列表，还是订单状态/金额等高频变更数据**
3. **能接受多长时间的数据延迟**
4. **订单状态变更后，是否已有可靠的失效机制**
5. **Redis 是否已经是团队标准基础设施**

## 暂定判断

- **多实例订单服务：优先 Redis。** 它解决的是共享缓存和跨实例一致的失效入口，但 Redis 本身不自动保证业务一致性，订单状态变更仍要主动删除或更新缓存。
- **单实例、纯查询优化、允许短暂旧数据：优先 Caffeine。**
- **订单状态、支付状态、金额、权限判断：不要让缓存结果成为业务事实来源。** 数据库仍是最终来源，缓存只能加速查询；这类数据应使用短 TTL 或状态变更时主动失效。
- **不要一开始就做 Caffeine + Redis 两级缓存。** 除非已经测出 Redis 网络延迟或访问成本是瓶颈，否则会额外引入双重失效、数据版本和击穿处理复杂度。

我现在倾向于：**如果这是常见的集群化订单服务，选 Redis；如果只是单体应用里的热点读缓存，选 Caffeine。**

```text
部署实例数：
缓存对象：订单详情 / 订单列表 / 订单状态 / 其他
允许旧数据：例如 1 秒、10 秒、完全不允许
读写比例：
Redis 是否已有生产级集群和团队运维规范：
```
