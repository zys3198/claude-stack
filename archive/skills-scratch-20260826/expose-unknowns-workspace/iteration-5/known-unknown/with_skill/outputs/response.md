## 1. 判级

**主级别：已知的未知。**

你已经明确了问题和两个候选方案，但还缺少会改变结论的约束。当前不能直接凭“订单模块”三个字拍板；不过也不应升级成“未知的未知”，因为候选方案和决策目标已经清楚。

需要特别暴露的隐含变量：

- 服务是单实例还是多实例、是否滚动发布
- 缓存的是订单详情、订单状态，还是幂等/辅助数据
- 是否允许读到旧数据，允许旧多久
- 订单写入后，其他实例是否必须立即看到新状态
- 是否已有 Redis 集群、监控、容量和故障预案
- 缓存失效由谁触发，能否覆盖取消、支付、退款等所有状态变更

## 3. 双向钢人检查

**最强支持 Redis 的理由**

- 多实例共享缓存，某个实例更新或删除后，其他实例能感知。
- 适合订单状态、支付状态这类跨请求、跨实例的数据。
- TTL、淘汰、容量和监控可以集中管理，滚动发布不会导致每个实例各自持有一份旧数据。

**最强反对 Redis 的理由**

- 多了一跳网络和序列化，Redis 故障会增加订单查询链路的复杂性。
- 运维、容量、连接池、热 Key、雪崩和故障降级都需要额外处理。
- Redis 只能提供缓存存储，不能自动解决数据库写入与缓存失效之间的一致性问题。

**决定性变量**

> 是否需要“跨实例共享 + 可控失效”，以及订单读到旧状态的业务风险。

## 4. 暂定判断

- **多实例 + 缓存订单详情/状态 + 写后需要跨实例可见：优先 Redis。**
- **单实例 + 主要是本地热点读取 + 允许短时间旧数据：优先 Caffeine。**
- **订单状态对正确性敏感时：不要把任何缓存当权威数据源；缓存只是数据库查询优化，必须先明确写入和失效顺序。**
- 如果两者都需要，常见组合是 **Caffeine 做进程内 L1，Redis 做共享 L2**，但这会显著增加失效和一致性复杂度，不应在没有性能证据时默认采用。

目前如果必须先选一个、且这是生产多实例订单服务，我会暂定 **Redis**；但最终结论取决于上面那组约束。
