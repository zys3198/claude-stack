# AI 文章润色 + 降 AI 检测率

## 0. 核心理念

**表面文字替换几乎无效。** 同义词替换、句式微调对降 AI 率收益极低--检测器看的是统计特征，不是个别用词。**根因（常识区原理）**：AI 是概率文字接龙，默认输出最高概率的常识答案（低困惑度）；L1 表层替换改的是常识区内措辞，困惑度依然低，检测器照判。要把文本推向非常识区，靠 L3/L4 改写作模式 + 注入真实智力，不是换词。真正两条正道：

1. **改写作模式**：从检测器指标（困惑度 / 突发性）出发，改变句式长度分布、词汇丰富度、结构规整度
2. **注入真实智力**：个人见解、实战经验、踩坑感悟--只有你自己能提供，AI 编不出来

降 AI 率 ≠ 绕过检测。是让文本真正更人化。同义词替换绕过 = 洗稿，本 skill 不教。

**关键认知**：朱雀检测的是"写作模式"，不是"内容"。它看你怎么写，不看你写什么。

---

## 1. 检测器原理（为什么被判 AI）

### 1.1 朱雀看什么

- **七维度分析文本特征**，建立文本"语义指纹"
- 三大逻辑：**困惑度、语义连贯性、词汇分布**
- 准确率约 92%，**但不绝对**--结构清晰、语言凝练的纯手写可能被误判为 AI
- 检测报告只作辅助参考，不是最终定论
- 持续迭代，2025 年 5 月更新后检测范围扩大、误判率降低

### 1.2 两个关键指标

| 指标 | 含义 | AI 倾向 | 人工特征 |
|------|------|---------|---------|
| **困惑度**（perplexity） | 文本可预测性 | 低（高可预测，每个词都在意料之中） | 高（低可预测，常有意料之外） |
| **突发性**（burstiness） | 句长变化 | 低（句长单一均匀） | 高（长短句交错） |

### 1.3 AI 特征 vs 人工特征

| AI 特征（被判定） | 人工特征（放行） |
|---|---|
| 词汇高度平均、高频通用词 | 自然跳脱、情感化用词 |
| 句长分布均匀（低突发性） | 句长高低交错（高突发性） |
| 过渡词模式化 | 非程式化过渡 |
| "总-分-总"规整结构 | 跳跃思维、突然类比、轻微跑题再拉回 |
| 低困惑度（高可预测） | 高困惑度（低可预测） |
| 机械式表达 | **人类写作的"不完美"特征** |

**最精辟的一句：保留人类写作的不完美特征，避免机械式表达。** 反直觉--不完美才是人味。

## 2. 交互流程（4 阶段）

本 skill 是多轮交互式的，不是一次输出完事。按以下阶段推进：

```
阶段 1: 诊断 -> AI 味分析 + 分区块评级 + 检测器视角诊断
阶段 2: 收集见解 -> 列出"见解注入点"，逐个问你，你来说，我来写
阶段 3: 执行改写 -> 按区块改写，融入见解，检测器指标驱动
阶段 4: 通读检查 -> 残留扫描 + 检测验证（朱雀 / contentany）+ 量化阈值验收
```

### 阶段 1：诊断

#### 1.1 全局评估
- 文章类型：教程 / 架构设计 / 踩坑复盘 / 技术选型 / 原理解析 / 其他
- 目标读者：默认面向**开发者**，语调**轻松专业**（不是学术腔，不是营销号腔）
- 整体 AI 味评级：🟢🟡🟠🔴

#### 1.2 分区块诊断

按文章自然段落或章节切块，每块标注：

- **AI 味等级**：🟢 尚可 / 🟡 轻度 / 🟠 明显 / 🔴 严重
- **检测器视角**：哪段低困惑度（高可预测）/ 低突发性（句长均匀）/ 词汇平均度高
- **问题类型**：句式单一 / 套话堆砌 / 过渡生硬 / 抽象空洞 / 缺实战细节 / 逻辑线性化 / 冗余啰嗦
- **具体问题句**：引用原文，说明为什么读着像 AI

问题按层级分类（改写优先级）：

| 层级 | 操作 | 降率效果 | 示例 |
|------|------|---------|------|
| **L1 表层** | 同义词、句式微调 | ★☆☆ | "显著提升"->"大幅提升" |
| **L2 结构** | 段落重组、过渡改写 | ★★☆ | 换隐性过渡，调段落顺序 |
| **L3 逻辑** | 改变论证思路和叙述路径 | ★★★ | 平铺罗列->先抛问题再论证 |
| **L4 见解** | 注入个人分析、实战经验、踩坑感悟 | ★★★ | "我踩过这个坑…原因是…" |

精力集中在 L3 / L4，L1 几乎无效。

#### 1.3 润色计划

汇总为可执行清单，附带迭代策略：

```
## 润色计划

### 迭代策略
- 第一轮：收集你的个人见解 -> L3/L4 深层改写（核心区块）
- 第二轮：L2 结构调整 + L1 表层打磨 + 检测器指标修正
- 第三轮：通读检查残留 AI 味 + 检测验证

### 按区块执行
#### 区块A（行 xx-xx）：[小标题] 🟠
- [ ] P0 (L4): [需要注入的见解类型]
- [ ] P1 (L3): [需要改变的逻辑结构]
- [ ] P1 (检测器): [突发性/困惑度怎么提]
- [ ] P2 (L1/L2): [表层打磨项]
```

### 阶段 2：收集你的个人见解（核心交互环节）

**这是最重要的一步。** 不会替你编造个人观点--那样出来的还是 AI 味。会找出文章中"适合注入你的真实见解"的位置，逐个问你。

对每个 🟠 / 🔴 区块，识别见解注入点：

```
### 注入点 1 - 区块 A，第 X 段
**原文**：[引用需要改造的句子/段落]
**这里缺什么**：[缺个人判断 / 缺踩坑经验 / 缺选型理由 / 缺"为什么不用 Y"的对比 / 缺性能数据]
**问你**：[具体问题，引导你说出真实想法]
```

问什么样的问题（技术文章常见空洞点）：

| 空洞类型 | 问法示例 |
|---------|---------|
| 选型没说为什么 | "你选 Redis 而不是 Memcached，实际原因？性能？生态？团队熟悉度？" |
| 只有结论没踩坑过程 | "你说'建议用连接池'--你什么场景下踩过不用的坑？当时什么现象？" |
| 列方案没做取舍 | "方案 A 和 B 你实际用了哪个？为什么放弃另一个？trade-off？" |
| 性能数据空泛 | "你说'性能提升显著'--具体从多少到多少？什么测试条件？数据量？" |
| 代码示例缺实战语境 | "这段代码在什么项目/场景里用？遇到什么边界情况？" |
| 原理解释太教科书 | "你第一次理解这个概念时，什么比喻帮你搞懂的？或踩过什么误解？" |
| 总结太官方 | "一句话总结这篇文章的核心教训，你会怎么说？" |

收集方式：
- **逐个注入点问**，不一次抛 10 个。每个等用户回答后再问下一个。区块多（>5）先问 P0 级。
- 用户说大白话、碎片化想法都行，我来组织成正式文字。
- 用户说"没有 / 跳过"-> 标记该点用 L3 逻辑改写兜底，不强行塞见解。

### 阶段 3：执行改写

收集到足够见解后，按区块逐个改写。

#### 3.1 改写原则
- 用户提供的见解是核心素材，优先使用，原汁原味保留思考过程
- L3 逻辑改写：根据见解内容重新组织论证路径
- L2 / L1 打磨：结构调整和表层润色
- 每个区块改写后展示 before -> after，说明改了什么

#### 3.2 检测器指标驱动（提高突发性 + 困惑度）

- **提高突发性**：长短句交错。拆长句为短句，或合并短句为带分号 / 破折号的复合句；加反问 / 感叹 / 设问打破陈述主导
- **提高困惑度**：打破可预测性。跳跃思维、突然类比、轻微跑题再拉回；论证重心前置 / 后置；插叙倒叙
- **降低词汇平均度**：高频通用词换具体形象表达；适当用专业术语 / 行业黑话（AI 倾向避冷僻词）
- **打破结构规整**：避免"总-分-总"和段落等长；减少"首先其次最后"标志连接词，改隐含逻辑承接

#### 3.3 技术文章特有的去 AI 味手法

**注入实战细节**
- Before: "在高并发场景下，系统性能会下降。"
- After: "去年双十一我们服务 QPS 涨到 8 万的时候，P99 从 50ms 直接飙到 2s--后来发现是连接池打满了，不是 CPU 的锅。"

**加入选型思考和 trade-off**
- Before: "推荐使用 Redis 作为缓存方案。"
- After: "我们对比了 Redis 和 Memcached，最后选 Redis 不是因为性能--两者差距不大--主要是因为我们需要原生支持的数据结构多，而且团队已经踩过 Redis 的坑，不想再踩一遍 Memcached 的。"

**用调试 / 排障叙事替代平铺结论**
- Before: "OOM 问题通常由内存泄漏引起，建议使用 heap dump 分析。"
- After: "那次 OOM 让我排查了整整两天。第一反应是看 GC 日志，发现 Full GC 频率正常，说明不是老年代撑爆的。后来 jmap 了一下，才发现是 ThreadLocal 里的缓存没清--每次请求创建一个大对象，请求结束不释放。heap dump 确认了这一点。"

**加入"我一开始以为…后来发现…"的认知反转**
- 人类写作最自然的思维轨迹，AI 很少主动写这种反转
- "我一开始以为这是网络延迟的问题，加了超时重试毫无改善。后来看了监控才发现，是下游服务在高峰期主动降级了，根本没处理请求。"

**用具体数字替代模糊描述**
- "性能提升显著" -> "接口 P99 从 1.2s 降到 200ms，TPS 提升了 4 倍"
- "数据量很大" -> "单表 2 亿行，每天新增 500 万行"

**数据与引用具体化**
- AI 倾向泛化（"近年来""大多数研究表明"）-> 换具体时间、地点、机构、可查证个案
- 必须真实，虚构数据比 AI 味更糟

#### 3.4 输出格式

每改完一个区块：

```
### 区块 A 改写 ✅

**Before**：
[原文段落]

**After**：
[改写后段落]

**改动说明**：
- L4: 融入你说的[见解摘要]
- L3: [逻辑改了什么]
- 检测器: [突发性/困惑度怎么提的]
- L1/L2: [结构/表层改了什么]
```

### 阶段 4：通读检查 + 检测验证

所有区块改完后，执行最终检查。

#### 4.1 残留 AI 味扫描

按「中文 AI 味句法信号清单」逐项扫全文，命中即改。这套清单针对中文，不是英文 prose 规则的翻译：

| # | 信号 | 表现 | 处理 |
|---|------|------|------|
| 1 | **衔接废话** | "接下来/下面/让我们/首先…其次…最后/综上/总而言之" | 直接删，让内容自己推进 |
| 2 | **排比三连滥用** | 三个同结构短句并列凑气势 | 砍到两句；中文靠排比强调没问题，AI 味在于"为凑三而凑三" |
| 3 | **分号/句号堆叠** | 长句靠分号串 3+ 小句，一句套一句 | 拆成独立短句 |
| 4 | **名词化滥用** | "高效化/可靠性/扩展性/颗粒度/鲁棒性" 堆砌 | 换成具体动词或场景 |
| 5 | **万能动词+名词** | "进行优化/实现提升/开展调研/采用方案" | 万能动词换成具体动词 |
| 6 | **"的"字连缀** | 名词前三个"的"做定语（"基于 XX 的针对 YY 的 ZZ 方法"） | 拆句或删修饰 |
| 7 | **程度副词空转** | "极大地/显著地/有效地/充分地" 无数据 | 删；或换具体数字 |
| 8 | **平衡腔** | "既要…又要…/不仅…而且…/一方面…另一方面…" | 挑一边说透，别端水 |
| 9 | **公众号腔设问** | "你是否遇到过…？/那么问题来了" | 直接陈述 |
| 10 | **双音节书面词堆叠** | "通过…的方式/在…的过程中/对于…而言" | 口语化 |

更完整的 AI 味清单见 `article-writer/references/ai-taste-blacklist.md`（含段首加粗标题、编号子标题、纯罗列表格等结构性信号）。

同时检查：
- 新引入的模板化表达（改写时可能不小心引入新 AI 味）
- 上下文不连贯的地方（各区块改完后拼接可能有缝隙）

#### 4.2 连贯性检查
- 区块之间的过渡是否自然
- 整体语调是否一致
- 注入的见解是否分布均匀（别全堆在一段）

#### 4.3 检测验证（关键闭环）

**改完不能凭感觉，要用检测器跑。** 单平台不够，交叉验证：

- **朱雀**（https://matrix.tencent.com/ai-detect/）：检测 AI 率、语义特征
- **contentany**：检测同质化、限流风险

两个平台互补：朱雀看 AI 率，contentany 看同质化 / 限流。单看朱雀可能 AI 率降了但同质化超了，反而被限流。

**AI 跨模型评估（检测器之外的补充）**：让另一个 AI 模型按**明确评分标准**挑改写后文本的毛病--标准要具体（句长是否有变化 / 有无套话 / 有无实战细节 / 开头是否绕弯），而非"帮我看看好不好"（否则 AI 拍马屁）。与朱雀+contentany 互补：检测器看统计特征，跨模型评估看语义人味。

无法联网检测时，用 Grep 本地验证残留：搜 `\*\*.+?\*\*`（加粗金句）、`不是.{0,30}而是`（二分对照）、`设计思想[一二三四五]|场景[一二三四五]`（编号子标题）等。

#### 4.4 量化阈值验收

| 指标 | 红线 | 超了怎么办 |
|------|------|-----------|
| AI 辅助占比 | ≤ 25% | 降低 AI 初稿比例，更多人工改写 |
| 同质化（contentany） | ≤ 20% | 重构内容框架，不只改措辞 |
| 暗限流指数（contentany） | ≤ 20% | 否则易被平台降权 |
| 朱雀 AI 率 | 目标 < 30% | 回阶段 3 针对低困惑度 / 突发性区块重改 |

超过红线 = 回阶段 3 重改，不是交付。

#### 4.5 验收评分卡（可选硬验收线）

全文交付前，对每个区块按 5 维打分（1-10），低于 35/50 的区块回到阶段 3 重写：

| 维度 | 判断问题 |
|------|---------|
| **直接度** | 开门见山，还是绕弯破题、铺垫半天？ |
| **节奏** | 句长有变化，还是齐刷刷排比 / 长句堆叠？ |
| **真实感** | 有真人 / 实战痕迹（数字、踩坑、反转），还是教科书腔？ |
| **信息密度** | 每句都承载信息，还是套话 / 废话占位？ |
| **口语度** | 像人说话，还是像机器翻译 / 书面公文体？ |

> 评分卡是辅助验收，不取代阶段 2 的见解注入--见解仍是去 AI 味的核心。某区块即使评分达标，若缺 L4 见解且本应有，仍算未完成。

#### 4.6 最终交付
- 输出完整改写后的全文
- 列出所有你提供的见解及其出现位置（方便确认没歪曲原意）
- 附检测验证结果（朱雀 AI 率 / contentany 同质化）或本地 Grep 验证摘要

## 3. 降 AI 率方法速查（10 类）

| 类别 | 做法 |
|------|------|
| **句式** | 长短交错、拆长合短、反问感叹设问、句式重构（提高突发性） |
| **词汇** | 高频通用词换具体形象、专业术语 / 行业黑话、同义词替换注意语义（降低词汇平均度） |
| **段落** | 打破"总-分-总"、跳跃类比跑题、减"首先其次最后"、论证重心前后置、口语化表述 |
| **数据** | 泛化换具体时间地点机构可查个案 + 个人案例 |
| **个人化** | 增加个人化表达、注入真实智力贡献、文体人化 |
| **标点** | 调整标点节奏 |
| **人工润色** | 隔夜修改法（放置数小时后读者视角重读）、请他人读、朗读检查拗口、增加批判性观点 |
| **工具辅助** | 仅参考：语义熵 + 句式频率图谱重组、被动转主动 / 长定语后置 / 直述转间接。工具是辅助，必须人工审校 |
| **交叉验证** | 朱雀 + contentany 双平台检测 |
| **根本** | 提升信息密度与情感价值；三层进阶：文体人化 -> 注入真实智力 -> 高级指令工程 |

## 4. 警告

- **避免翻译法**：中翻英再翻中，出来还是 AI 味，且语义常失真
- **避免山寨工具**：多数"一键降 AI"工具是粗暴同义词替换，效果差且可能引入语病
- **避免虚构数据**：比 AI 味更糟，是事实错误
- **固定套路会失效**：朱雀持续迭代，任何固定应对方式都可能随时间失效。组合使用方法，不依赖单一技巧
- **避免过度依赖 AI 初稿**：AI 初稿比例越高，改写难度越大

---

## 5. 边界（重要）

- **不洗稿**：同义词替换 + 句子重组绕过检测 = 洗稿，违反 `article-writer` §1。本 skill 教的是改写作模式 + 注入真实智力，让文本真正更人化
- **工具仅参考**：小发猫 / PaperBERT / 汇创鸭等是商业产品，方法可借鉴，不推广使用。其"同义词替换"本质与"不洗稿"有张力
- **正道**：三层进阶--文体人化（改写作模式）-> 注入真实智力（个人见解）-> 高级指令工程（prompt 引导 AI 生成更人化内容）
- **根因治理优先**：若 AI 味源于"一次性生成没搭骨架"（非纯文风问题），事后 polisher 治表不治本--回 `article-writer` §7.10 搭骨架四步法从源头重搭，再回来 polisher。视频观点"问题不在提示词在流程"
- **忠于原意**：不改技术事实、数据、代码逻辑。不确定时保留原文
- **技术准确性优先**：去 AI 味不能牺牲技术准确性。模糊口语若影响技术理解，宁可保留书面表达
- **用户是见解来源**：绝不为用户编造个人观点、虚构踩坑经历、捏造性能数据。没有用户输入的见解就用 L3 逻辑改写兜底
- **篇幅控制**：长文（>5000 字）分批处理，每次 2-3 个区块，避免一次改太多丢失上下文
