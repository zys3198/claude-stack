# 本机 Docker 使用约定

三条目的：**限制占用**（单个容器不能吃光本机内存与进程数）；**只在容器内执行**（任何要执行的命令都放容器里）；**安全性**（容器内进程不得提权，宿主机的独占资源同一时刻只有一个使用者）。

## 要执行命令时

宿主机不装工具链也不跑命令。按顺序选去处：

1. 项目里有对应服务：`docker compose -f deploy/docker-compose.local.yml run --rm <服务> <命令>`。
2. 项目里没有对应服务：起一个一次性容器。

```bash
docker run --rm \
  --memory 2g --memory-swap 2g --pids-limit 512 --cpus 2.0 \
  --security-opt no-new-privileges:true \
  -v "$(pwd)":/work -w /work \
  node:22-bookworm-slim \
  bash -lc "<命令>"
```

- 只读的活（看版本、读文件）挂载加 `:ro`：`-v "$(pwd)":/work:ro`。
- 命令要写文件时挂可写，产物落在工作树里，中间文件放 `.claude/tmp/`。
- 内存上限、进程数上限、CPU 上限与 `--security-opt no-new-privileges:true` 一个都不能省，取值按本机规格定。
- 一次性容器默认使用 `--rm`，退出后自动删除一次性容器；常驻服务使用 `docker compose up -d` 并登记台账。
- 需要新的工具链时装进镜像或一次性容器，不装到宿主机。

## 可销毁边界

容器随时可销毁，因此**不可重建的东西一个都不许只存在于容器里**。判据只有一条——路径落不落在挂载点之下，不需要检查脚本：

- **挂载点之下**（`/work`）：宿主同一路径有同一份，容器销毁了它还在。
- **容器匿名层**（`/root`、`/tmp`、`/usr/local` 等未挂载路径）：容器销毁即丢，这里只许放可重建物——装好的依赖、构建中间产物、下载缓存。

据此三条做法：

1. 工作树一律**挂载**进去，不复制进去。`docker cp`、镜像里的 `COPY`、容器内重新 `git clone` 出来的副本都不是挂载，不能当作工作副本使用。
2. 不可重建的产物必须写进挂载点。测试证据、数据库导出、要留的日志落 `/work` 之下；落到 `/tmp` 等于任务结束时自动丢弃。
3. 收尾时在**宿主**上确认要留的东西真的在。`--rm` 容器退出后取不回，这一步无法自动化，是唯一的兜底。

常驻容器与一次性容器同规矩：`docker exec` 进去产出的东西，同样只有在挂载点之下的才算保住。

## 用户已确认的 Docker 授权边界

Docker 容器内的真实业务写入、数据库写入、验收测试数据、服务启动/停止/重建和容器内脚本默认直接执行，不逐项请求确认。一次性测试容器只要没有命中 `session-hygiene.json` 中正在运行的独占目标，不进入共享资源确认线；命中独占目标且存在其他活跃会话时，按精确授权范围复用或提请确认。涉及宿主机文件、绑定挂载数据、宿主机端口或外部系统的操作，仍按影响范围逐项确认；删除数据库卷、其他可能含数据的资源，以及任务结束清理仍执行下方清理确认线。

## 任务结束时清理

每次任务结束前盘点本次创建或修改的容器、网络、卷、镜像、构建缓存、日志和挂载目录产物；一次性容器默认使用 `--rm` 自动清理；常驻服务可直接执行 `docker compose down --remove-orphans`；卷、数据库文件、挂载目录内的生成物和其他可能含数据的资源仍按下方清理确认线处理。

卷、数据库文件、挂载目录内的生成物和其他可能含数据的资源，必须列出准确路径与内容用途；未获该资源或范围授权时询问是否删除，已明确授权时直接执行且不重复询问；需要保留的产物写明保存路径和原因。删除完成后再次检查容器、卷、相关目录和台账，确认本次任务的处理结果已记录。

## 机械保证

`~/.claude/hooks/scripts/resource-guard.py` 挂在 `settings.json` 的 PreToolUse 上，拦截客观可判定的动作：compose 文件里新增的服务缺 `mem_limit` 或 `security_opt`；变更 `session-hygiene.json` 独占清单里正在运行、且本机另有活跃会话的容器；远程 Git 和生产/真实数据变更在未获得精确授权时进入确认线；在宿主机上执行 pnpm、mvn、java、node 这类构建工具链时直接阻断。

**失败时怎么走，按资源性质分两类**（与 hook 判据 H4 一致）：

- **共享资源类一律 fail-closed**：独占容器状态、其他活跃会话数、授权状态这三项读不到时，hook 返回 `ask` 而非放行。`running_containers()` 读不到 `docker ps` 时返回 `None` 而不是空集合——「枚举失败」与「确实没有容器在跑」必须分开表达，否则失败会被当成「都没有在跑」而被放过。`other_session_count()` 同理。
- **普通路径 fail-open**：hook 自身异常、payload 解析失败、命令形态认不出时放行，不堵干活。这类降级必须留下日志。

资源状态或授权状态无法确认时**不静默放行**；普通路径的放行与降级则写进 `~/.claude/resource-guard.log` 备查。

判据细节、边界与已知覆盖不到的情形写在脚本头部注释里，要改判据就看那里。Hook 不代替主模型做 R0-R4 语义分类。

**二、删除判据。** 满足其一即删：内容已在 `resource-guard.py` 或项目的 compose 文件里 → 删，它是缓存；被本文件后面条目覆盖 → 删旧条；只在特定情形才用到 → 下沉 `references/`；指向的目标已不存在 → 删引用，或改指向。
