# Instruction Engineering — 项目指令资产

本 Skill 管两类工作，都只产出草稿或 diff，不直接修改项目文件：

- **建立**：为项目产出 AI 上下文（CLAUDE.md / AGENTS.md / 模块说明草稿）。
- **审查**：审查已有指令文件的指令设计，输出有证据的最小修改 diff。

两类工作都要先明确纳入范围，再动手。范围之外的文件标为“不在范围”，不顺手处理。

---

# 第一部分：建立项目 AI 上下文

让项目能被 AI 看懂。AI 在老项目里判断错，根因是**上下文不够**：AI 与开发的差别不在能力，在于上下文。缺的是四类：

1. **业务历史背景 + 整体协作方式**（与其他模块的关系）
2. **过去的需求/技术文档位置**（往往在开发或产品脑袋里）
3. **项目真实运行情况**：哪些代码真在跑、哪些只是历史兼容但跑不到（引用 ≠ 运行）
4. **架构设计 + 技术债务**：哪些改造只做了一半

目标：**同一件事，只需要跟 AI 强调一遍即可**——建好一次，AI 后续无需每次重建上下文。

## 何时用

- 用户说「让 AI 看懂这个项目 / 梳理项目给 AI 用 / 建 CLAUDE.md / 建 AGENTS.md / 项目 AI 上下文」
- 要在项目里引入 AI 协作、重构为 AI 可维护项目
- 老项目债务重、AI 总判断错、想给 AI 补上下文

不用：改代码或重构实现（走 code-change-workflow-by-user）、写技术文章、知识库或图谱建设。

## 先分清是模型问题还是项目问题

同一个需求在老项目上兜圈子、漏需求、改崩无关文件，在新项目上正常，症状落在项目侧积累。判断办法是开一个干净的小项目，用同一需求再跑一遍：

- 新项目正常 → 问题在项目积累，走本 Skill。
- 两边都差 → 先排除模型侧和任务描述本身的问题，不把本 Skill 当解法。

这个对照只给出方向，不定位具体是哪类垃圾。具体定位走下面的执行流程和「债务观察清单」。

## 产物

产出到 `docs/ai-context/`，**不直接改项目文件**，用户审阅后自行落地：

```
docs/ai-context/
  CLAUDE.md 草稿       壳：@AGENTS.md 导入 + Claude Code 特有内容
  AGENTS.md 草稿       源：知识索引 + 项目规范（Copilot/其他 agent 读）
  analysis-report.md   分析报告：模块切分、依赖、真实运行链路、债务观察
  modules/<module>-AGENTS.md   模块领域说明（就近落盘）
```

## 执行流程

1. **摸底**：目录树、语言/框架、构建配置、README；**先检查是否已有 CLAUDE.md / AGENTS.md / .claude/rules/**（增量场景先读已有内容再决定补什么）。摸底须覆盖上文四类上下文——业务背景与协作方式、文档位置、真实运行 vs 死代码、架构债务；每类记录证据来源，查不到就标「未验证」
2. **模块切分**：核心模块 + 依赖关系
3. **真实链路识别**：入口/路由/构建产物，区分活代码 vs 死代码（引用 ≠ 运行）
4. **领域知识提炼**：业务背景、架构、规范、三方对接
5. **强约束问答**：向项目负责人确认运行真相、债务、文档位置；未确认项标记「未验证」，不写"已验证"结论。**找不到负责人时：全部标「未验证」并注明证据缺口，继续产出草稿**
6. **产出**：报告 + CLAUDE.md/AGENTS.md/模块草稿

问答若推翻步骤 2-4 的结论（模块切分/链路判断），回到对应步骤修正后继续。

## 完成条件

- `analysis-report.md`、根 `CLAUDE.md` 草稿、根 `AGENTS.md` 草稿和适用的模块说明均已列出；不适用项说明原因。
- 业务背景、文档位置、真实运行链路、架构债务四类上下文各有证据，或明确标记「未验证」及证据缺口。
- 未覆盖已有文件，未把推断写成已验证事实；所有待负责人确认项和剩余风险已列出。
- 只完成上下文产出，不把代码重构、项目落地或运行生效当成本 Skill 的完成条件。

## 债务观察清单（分析报告 §5 用，只报告不改）

用此清单当 lens 逐项扫项目，产出到分析报告「债务观察」：

1. **死代码**：有引用但真实链路跑不到。判据：引用 ≠ 运行；运行条件藏在环境变量/配置开关时开发也难辨。典型：复制粘贴旧客户端兼容改造遗留的环境判断 if/else；设计了未落地的架构残留（如 OT 协同最终只是 HTTP 同步，却保留多套消息通信方式）；功能迁移新模块后旧链路未清、新旧耦合。
2. **过度设计**：为幻想未来加的复杂度——无业务诉求的协同/抽象/可配置性。教训：过度设计不可怕，可怕的是改造不彻底 + 几轮重构不彻底叠成债务。
3. **半成品改造**：专项改造起头未做彻底，遗留尾巴层层叠加。
4. **命名/结构混淆**：近义类名多，AI 定位易错（如 dtsf 的 Oa*Service 55 个、`OaAttendanceService` vs `OaHrAttendanceService`）。产出时把撞车清单写进对应模块说明。
5. **文档与运行脱节**：文档说在跑实际是死代码；或目录存在但无归属说明。

## 文件策略

Claude Code 不读 AGENTS.md，只读 CLAUDE.md。用 `@AGENTS.md` 导入实现单源双生态：

```markdown
<!-- CLAUDE.md -->
@AGENTS.md

## Claude Code 特定内容
...
```

AGENTS.md 是内容源（Copilot 等读），CLAUDE.md 是壳（Claude Code 读同一份）。**不双写同内容**。官方推荐 @ 导入而非双写或 symlink（Windows 上 symlink 需管理员权限或开启开发者模式）。

## 维护规则（写入 AGENTS.md 草稿）

- 目标：「同一件事只跟 AI 强调一遍即可」——知识落盘使 AI 后续无需每次重建上下文
- 根目录只保留索引概要（路径 + 1~2 句摘要），不堆细节
- 根入口 ≤120 行预算：接近 115 行就把细节迁到详情文档，入口只留摘要和链接
- 对话中出现可复用内容时，就近落盘到对应模块，并同步更新根索引。可回填的五类：本次用到的命令、项目代码风格约定、有效的测试方法、环境与配置怪癖、踩到的坑与绕法
- 索引过期或不准确时主动修改
- 落地说明：草稿集中产出到 `docs/ai-context/modules/`，**落地时**将各模块说明就近放置到对应模块目录（如 `src/auth/AGENTS.md`），根索引路径同步指向实际位置

# 第二部分：审查指令设计

把一组指令文件当作一个系统审查，减少误触发、上下文浪费和过早停止，同时保留安全、权限、业务和验收门禁。

## 范围

只读取用户明确纳入的：

- 自建 Skill 的 `SKILL.md`
- `CLAUDE.md`
- `AGENTS.md`

不读取或审查 `references/`、`scripts/`、插件 payload、外部 Skill 或其他文件。来源不明确的文件标为“不确定”，不按目录位置猜测归属。

本部分只出审查报告和 diff，不执行 `Edit`、`Write`、移动、删除、提交或推送。

## 审查基准

- description 尽可能短，只说明 what 和 when；根文档是最小路由器。
- 详细资料按任务需要读取，不把无关文档设成每次必读。
- 工作流不要写成限制模型判断的固定长食谱；保留真正不可猜的约束。
- 开始任务前定义可观察的完成条件；探索任务同时定义探索范围和停止点。
- 安全且目标明确的动作不因流程习惯停住；确有风险、权限或用户决策时才等待。

## 审查流程

### 1. 定靶

列出文件路径、文件归属、审查目的和允许范围。保留已有改动，不扩大文件范围。每个目标文件都要有以下结论之一：已审查、未读取、读取失败或不在范围。

### 2. 七项检查

对每个目标文件逐项输出 `PASS / FAIL / 不确定`、位置、原文、影响和证据。

| 检查项 | 通过标准 |
|---|---|
| 触发边界 | 有具体正向信号和负向边界；不把相关领域、单个关键词或“任何/其他/等等”当成无条件触发 |
| 重复与冲突 | 同一规则只有一个权威位置；不同文件的优先级、例外和动作一致；不重复要求模型本来会做的常规检查 |
| 资料读取 | 只在资料会改变当前判断、执行或验收时读取；按需路由，不强制预读任务外材料 |
| 等待边界 | 每个等待点有风险、权限或用户决策理由；安全明确的动作可继续；必要 checkpoint 不被删除 |
| 完成标准 | 开始前写明可观察完成证据、停止点和失败/阻塞状态；不把文件存在、配置声明或“已执行”当作生效证据 |
| 留存依据 | 每条规则能说出为什么要留下它；说不出依据的列为删除候选，不靠「删了怕出事」保留。反向判据：代码里一眼可见的信息、通用最佳实践、不会复发的一次性修复、能压成一行的冗长解释，都不该留下；终检问一句「新会话读到这条有用吗」。规则文件只会单向膨胀，这一项是唯一能同时抑制膨胀和暴露无效规则的检查 |
| 时效核对 | 文档描述与仓库现状一致：命令能真实跑通、引用的文件仍存在、技术版本与目录结构未过期、多个指令文件不重复同一份信息。跑不通的命令、指向已删文件的路径、过期的版本列为必须修正项，不因「文字本身没错」放过 |

### 3. 证据分级

每项判断标注一种或多种证据：

- `[源码]`：目标 Markdown 当前文字直接证明。
- `[执行记录]`：真实运行日志、产物或测试输出证明；没有记录就不能声称发生过事故或已生效。
- `[官方原则]`：文章或官方文档提出的通用原则。
- `[规则推测]`：根据静态规则推断的风险，必须写明尚未观察到实际影响。
- `[未知]`：缺少决定结论所需的文件或运行证据。

静态文字不等于运行行为。没有执行记录时，把结论写成“规则推测”或“未验证”。

### 4. 输出发现

每条 `FAIL` 或有必要的最小改进都必须包含：

```text
文件位置：<path:line>
当前原文：<最小完整摘录>
适用场景：<什么输入或任务会触发问题>
证据类型：<源码 / 执行记录 / 官方原则 / 规则推测 / 未知>
影响：<误触发、上下文浪费、重复执行、过早停止或验收失真>
最小修改 diff：
<unified diff>
保留约束：<安全、权限、业务、验收或用户确认线>
```

只报告能改变行为的改动；全部通过时报告“无须修改”，不凑 diff。

## 不得削弱的约束

不得把效率建议变成以下门禁的删除理由：

- 推生产、删除不可恢复数据、对外发送或发布；密钥修改、数据库迁移、生产脚本执行并入对应门禁。
- 技术栈变更、数据结构调整、关键业务分支、权限或角色判定修改前的确认和依据检查。
- 子代理启动前展示实际可见的模型、provider、route、effort、并发数和隔离方式，并等待用户确认。
- 代码或业务任务的真实运行、验收、失败修复、重新验证和独立复核。
- 业务要求的多来源核验、实验授权、用户确认、数据保留和审计记录。

可以收窄触发、改成按需读取或合并重复文字，但不能把必要权限、风险判断或业务验收改成“模型自行决定”。

## 审查完成条件

审查完成必须同时满足：

1. 所有纳入范围的文件都有结论；未读取项明确标记原因。
2. 每条建议都有原文、场景、最小 diff、证据类型和保留约束。
3. `[执行记录]`、`[官方原则]` 和 `[规则推测]` 没有混写。
4. 未执行文件修改；未验证内容标为 `unknown`、`not-run` 或“未验证”。
5. 报告末尾给出一个最小下一步，或明确“无需修改”。

# 边界

- 建立部分：只产出上下文草稿，不把代码重构、架构简化、测试建设当成本 Skill 的工作。
- 审查部分：只出报告和 diff，不改文件，不扩到 `references/`、`scripts/`、插件或外部 Skill。
- 两部分都遵守：未验证内容标「未验证」，不把推断写成事实；不把文件存在或配置声明当作生效证据。
