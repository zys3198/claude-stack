# ai-coding-guide 准确性优先重构设计

- 日期：2026-07-07
- 目标对象：`C:\Users\zys31\.cc-switch\skills\ai-coding-guide`
- 当前定位：Claude Code 专用 skill
- 本文性质：设计文档，只定义目标、边界、结构、校验规则与执行顺序；不展开实现计划

## 1. 背景

`ai-coding-guide` 目前同时承担了路由器、生态说明书、历史维护账本三种角色，导致三个直接问题：

1. 主文件过重，影响首屏路由效率。
2. 历史迁移残留较多，容易混入非 Claude Code 视角、过时生态、口气过满的断言。
3. 推荐结论、证据来源、维护规则耦合在一起，后续修订时容易出现局部修补后再次漂移。

本轮不把它做成“更全”的指南，而是把它收窄成“更准”的 Claude Code 路由器。

## 2. 目标

本轮只追三个核心结果：

### 2.1 死引用清零

清除当前环境下不存在或不可作为默认推荐的：

- skill 名
- slash 命令
- 命名空间
- 插件归属
- 目录路径
- IDE 能力映射

### 2.2 事实表述收紧

对装机状态、生态归属、数量、能力边界、默认流程做分级处理：

- 本地已证实：可以直接写结论
- 官方可证实：可写结论，但标注非本机实测
- 经验判断：保留为推荐，不写成事实
- 证据不足：不直接定论，必要时停下来问用户

### 2.3 推荐语气降火

把“经验偏好”“当前装机偏好”“维护者判断”与“硬事实”分开表达，避免把偏好包装成定律。

## 3. 非目标

本轮明确不做以下事情：

1. 不做多 IDE 通用指南。
2. 不补全生态大全，不追求覆盖所有可选插件或外部工具。
3. 不做大规模文风润色。
4. 不为了形式好看做大拆大建。
5. 不在证据不足时硬补看似完整的结论。

## 4. 定位与边界

重构后，`ai-coding-guide` 的定位是：

> Claude Code 当前环境下的 AI 编码生态路由器。

它负责回答：

- 这类任务该先走哪条流程
- 该用哪个 skill 或生态
- 哪些推荐是本机当前默认项
- 推荐的证据等级是什么

它不负责：

- 充当所有生态的百科全书
- 代替下游 skill 的完整执行说明
- 为未安装生态提供默认主路径
- 维护与当前主环境无关的广谱 IDE 视角

## 5. 设计原则

所有改动按以下四条裁决：

1. 真装了 > 理论上可装
2. 本地实测 > 二手总结
3. 明确边界 > 看起来全面
4. 少写错 > 多写满

## 6. 信息结构与文件分工

### 6.1 `SKILL.md`

主文件只保留三类内容：

1. 触发条件与角色定位
2. 决策流与分流规则
3. 高频最小速查

主文件不再承担以下职责：

- 长篇生态介绍
- 多 IDE 对照大全
- 大量维护历史说明
- 细粒度证据账本

主文件目标是“能快速路由”，不是“把所有背景一次讲完”。

### 6.2 `references/ecosystems.md`

承接按需展开的深层内容：

- 生态定位
- 重叠区处理
- 降级策略
- 为什么推荐 A 而不是 B

该文件会从“多 IDE 全景”收缩为“Claude Code 当前环境视角下的生态说明”。

处理原则：

- 与 Claude Code 当前环境无关的内容删除或压缩为极小附录
- 仅保留对当前路由判断有帮助的生态细节
- 不再把未安装生态当默认路径描述

### 6.3 `references/MAINTENANCE.md`

只保留维护规程：

- 什么时候必须更新
- 更新时先查什么证据
- 改完后需要同步哪些文件
- 变更记录怎么写

该文件不再承担推荐正文职责，避免“维护手册”与“路由正文”交叉污染。

### 6.4 `test-prompts.json`

用途收窄为高频路由回归样例。重点覆盖：

- “该用哪个 skill”
- “A 和 B 怎么选”
- “该不该先走流程”
- “这个任务是否该直接答，不要启动重流程”

不把它做成百科问答集。

### 6.5 `scripts/audit.ps1`

改造成 Claude Code 保真巡检脚本，优先扫描：

- 死 skill 名
- 死 slash 命令名
- 非 Claude Code 视角残留
- 过时路径
- 容易过满的措辞
- 需要人工复核的断言位点

脚本定位是“抓疑点”，不是“自动判真”。

## 7. 准确性治理规则

### 7.1 信息分级

#### A. 本地已证实

来源包括：

- 当前会话 system reminder
- `~/.claude/skills/`
- `~/.claude/plugins/cache/`
- 本地脚本与配置
- 当前环境可见的工具、agent、skill

表达方式：

- “本机已装”
- “当前会话可用”
- “本地扫描可见”

#### B. 官方可证实

来源包括：

- 官方文档
- 官方仓库 README
- 官方 marketplace 元数据
- 官方插件说明

表达方式：

- “官方文档显示”
- “官方元数据声明”
- “未在本机会话实测”

#### C. 经验判断

保留为推荐，但必须降级表述。

表达方式：

- “默认建议”
- “经验上更适合”
- “对当前环境更省事”
- “通常更稳”

禁止写成：

- “唯一正确做法”
- “一定更好”
- “必须如此”

除非确有硬门禁且证据明确。

#### D. 证据不足

处理规则：

- 影响主推荐结论：停下来问用户
- 不影响主结论：标“不确定”或“待核”
- 纯装饰信息：直接删除

### 7.2 三类问题的修正优先级

#### P0：直接误导路由

包括：

- 死 skill / 死命令 / 死路径
- 把别的 IDE 方案当 Claude Code 默认路径
- 装机状态写反
- 官方归属写错

#### P1：误导理解但不一定立即走错路

包括：

- 能力边界说太满
- 数量或规模断言不稳
- 把推荐写成事实

#### P2：维护性问题

包括：

- 主文件承载过多细节
- 同一结论多处重复
- 规则散落导致后续继续漂移

## 8. 实际执行顺序

### Phase 1：证据盘点

先建立问题清单，不先改正文。

盘点内容：

1. 当前会话可用项
2. 本地已装项
3. 文件内现有断言
4. 非 Claude Code 视角残留
5. 高风险过满措辞

### Phase 2：逐类修正

按 P0 → P1 → P2 顺序处理。

### Phase 3：轻度重排

仅做支撑准确性的结构调整：

- 长解释从 `SKILL.md` 挪到 `references/*`
- 同类规则集中表达
- 推荐型内容与证据型内容分层
- 非 Claude Code 相关附带内容压缩或删除

不做：

- 为整齐而重命名大量节点
- 新建成组文件
- 把 skill 重写成百科全书

## 9. 文件级改动范围

默认允许改动以下文件：

- `SKILL.md`
- `references/ecosystems.md`
- `references/MAINTENANCE.md`
- `test-prompts.json`
- `scripts/audit.ps1`

如确实需要新增文件，限制为一个小型 reference 文件，且必须满足两条：

1. 能减少主文件继续漂移
2. 不是为了“显得专业”而增设结构

## 10. 风险与回退

### 10.1 主要风险

#### 风险一：修准了，但变钝了

表现：

- 什么都写“不确定”
- 路由器失去推荐价值

处理：

- 保留经验判断
- 但明确是经验判断，不伪装成事实

#### 风险二：删多了，信息断层

表现：

- 主文件变轻
- 但用户看不出推荐依据

处理：

- 不是纯删，而是主文件保决策、reference 保解释

#### 风险三：Claude Code 专用化不彻底

表现：

- 仍混有 Codex / opencode / Cursor / Windsurf 术语
- 主语不统一，口径前后不一

处理：

- 统一以 Claude Code 为主语
- 非当前环境内容删除、压缩或降为非默认说明

#### 风险四：巡检脚本假阳性过多

表现：

- 脚本把正常语句也报错
- 后续维护噪音高

处理：

- 脚本只提示疑点
- 人工最终判定

### 10.2 回退策略

按三层回退：

1. 文案级回退：回退单条表述
2. 结构级回退：把不适合外置的段落移回主文件
3. 文件级回退：单文件撤销，不拖全局

原则：

- 不做不可逆大拆
- 每一步都能单独撤回

## 11. 验证方式

重构完成后做三层验证：

1. 机械扫描：`audit.ps1` 扫死引用、路径残留、口气过满提示词、疑似跨 IDE 残留
2. 路由回归：用 `test-prompts.json` 覆盖高频问题，检查是否仍会分流错
3. 人工抽检：抽最关键推荐，看能否追溯到本地证据、官方来源或明确的经验判断标签

## 12. 验收标准

### 12.1 必须满足

- `SKILL.md` 明确为 Claude Code 专用
- 不再把其他 IDE 方案当默认推荐
- 高风险死引用清理完毕
- 关键推荐表述不再口气过满
- 主文件与 reference 文件职责分明
- 碰到影响主推荐结论的证据不足点，不擅自替用户决定

### 12.2 应该满足

- `scripts/audit.ps1` 能扫出主要准确性风险
- `test-prompts.json` 能覆盖高频路由问题
- 主要推荐能明确归类为“本地实证 / 官方说明 / 经验判断”之一

### 12.3 不作为本轮门槛

- 文风完全统一
- 历史痕迹完全消失
- 文档缩到最短
- 覆盖全部生态大全

## 13. 本轮完成定义

本轮完成后，`ai-coding-guide` 应满足四个结果：

1. 更窄：只服务 Claude Code 当前环境
2. 更硬：少拍脑袋，多证据
3. 更稳：后续不易再次漂移
4. 还够用：依然是能快速分流的路由器，而不是被删成空壳

## 14. 流程约束说明

按上层工作规则，提交 commit 需要用户明确确认。因此本设计文档会先写入、先自检、先交用户审阅；是否 commit 在用户审阅后单独确认，不自动执行。
