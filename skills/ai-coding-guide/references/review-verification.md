# 审查验证链（运行验证 + 敏感信息清理）

本文件只在 AI 代码审查/交付前验证场景展开。`routing.md` 只留「审查要走验证链」一行；本文件存完整两步。

**触发：** 审查 AI 生成的代码、写 PR/审查评论、或交付前验证时 → 读本文件，按两步走。

## 第一步：先运行验证，不只静态看代码

代码能运行 ≠ 产品正确，但「能构建 + 能跑过真实场景」能击穿纯看代码发现不了的问题（系统设计、UI 可用性、缺上下文）。静态审查只能发现你能想到的问题，跑一遍能发现没想到的。

改后代码可构建可运行时，先构建 + 运行（测试、冒烟、或两者）：

1. 构建并运行修改后的代码。
2. 覆盖正常路径 + 边界条件 + 至少一个对抗式场景（作者没预料的输入）。
3. 记录证据：跑了什么、命令、exit status、失败案例。

无法构建或运行（无工具链、无测试、依赖外部服务）时，在报告里明说「未运行验证」，不假装验证过。

## 第二步：输出前清理本地环境指纹

运行验证可能接触本地服务。写 PR/审查评论前，扫一遍报告，移除会泄漏环境的本地信息：

- 用户名、IP、主机名
- 集群名、命名空间
- 凭据、内部 URL
- 绝对本地路径

保留结论，去掉指纹。AI 验证时跟本地服务交互后，容易在「展示证据」时把环境信息带进公开内容。

## 边界

- 验证比静态审查更可靠，但需求、架构、体验、安全策略和「是否值得做」仍由人判断——验证链是「AI 审 AI」的护栏，不是替代人的裁判。
- 对抗式审查比「帮我看看有没有问题」有效得多：主动找茬，不只被动检查。
