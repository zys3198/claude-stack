# review-doc：多 Agent 并行技术文章审校

对中文技术文章进行 4 维度并行审校，聚合输出结构化报告。用户确认建议后批量执行修改。

---

## 工作流程

### Phase 0：前置检查

1. 确认待审文件路径。若用户仅粘贴文本，先保存为 `.md` 文件。
2. 确认用户是否已有 `tech-article-review` skill——若有，告知用户本 skill 与 `tech-article-review` 的区别（见对比表）。
3. 若文件过大（>500 行），询问用户是否只审指定范围。

**与 tech-article-review 对比：**

| 维度 | tech-article-review | review-doc |
|------|-------------------|------------|
| Agent 数 | 1 个 | 4 个并行 |
| 审校方式 | 逐段增量 | 分维度并行后聚合 |
| 修改方式 | 出 patch 列表 | 出报告 → 用户确认 → 批量改 |
| 适用场景 | 快速评审、多轮增量 | 深度审校、首次全量 |
| 输出 | 对话内 patch | 独立报告文件 |

---

### Phase 1：派发 4 个并行 Agent

在单次对话中**同时派发** 4 个独立 Agent，各自读取完整文档后执行专项审查。每个 Agent 独立输出发现。

#### Agent 1：事实核查员（Fact Checker）

**目标**：找出所有事实错误、技术偏差、过时信息。

核验方向：
- 技术主张是否有依据（架构原理、协议规范、版本行为）
- 数字、版本号、日期、性能指标是否准确
- 技术对比是否在等价条件下进行
- 因果关系是否成立（A → B 是否属实）
- 引用的外部信息/数据是否可查证

对于每个问题，标注：
- 原文位置（段落号或行号）
- 问题描述
- 修正建议
- 严重性（见分级标准）

#### Agent 2：一致性检查员（Consistency Checker）

**目标**：找出术语混用、前后矛盾、逻辑断层。

核验方向：
- 同一概念是否使用了不同术语（如 ES / Elasticsearch 混用）
- 前后数据/结论是否一致（前文说 3 种方案，后文只出现 2 种）
- 逻辑流程是否完整、有无跳跃
- 中文/英文术语策略是否全文统一
- 上下文引用是否正确（如"如上所述"但上文并未提及）

#### Agent 3：风格检查员（Style Checker）

**目标**：优化语言表达，消除 AI 腔，提升可读性。

核验方向：
- AI 痕迹："首先 / 其次 / 总的来说 / 值得注意的是"等模板化起手式
- 被动语态、冗余修饰、长难句
- 技术术语是否符合中文技术写作规范
- 中英文标点混用、大小写规范
- 段落过长需要拆分
- 句子主谓结构是否清晰

#### Agent 4：结构检查员（Structure Checker）

**目标**：评估文章组织、信息流和读者体验。

核验方向：
- 标题层级是否合理（无跳级：H1 → H3 中间缺 H2）
- 信息密度是否均衡（某段极长、某段极短）
- 是否有缺失的必要段落（前置知识、异常处理、总结）
- 读者能否按顺序理解文章而不需要回读
- 文内标题是否准确反映内容

---

### Phase 2：聚合与去重

等待 4 个 Agent 全部完成后：

1. **合并所有发现**到一个列表中
2. **去重**：相同位置、相同问题的发现只保留一条，合并 Agent 来源
3. **按严重性排序**：P0 → P1 → P2
4. **去噪**：移除无实质改进价值的微调项
5. **统计**：总计发现数、各严重级别数量、各 Agent 贡献数

---

### Phase 3：生成审校报告

在目标文档同级目录下生成报告文件：`<原文件名>.review.md`

报告格式：

```markdown
# 审校报告：<原文件名>

## 摘要

- 总发现：N 条
- P0（严重错误）：N 条
- P1（重要优化）：N 条
- P2（轻微建议）：N 条
- 审校时间：YYYY-MM-DD HH:mm

## 各 Agent 贡献

| Agent | 原始发现数 | 合并后有效数 |
|-------|-----------|------------|
| 事实核查 | N | N |
| 一致性 | N | N |
| 风格 | N | N |
| 结构 | N | N |

## 修改建议

### P0 — 严重错误（必须修改）

[原文位置（段落/行号）] **问题**：[一句话描述]
**建议**：[具体修改方案]

### P1 — 重要优化

...

### P2 — 轻微建议

...
```

---

### Phase 4：用户确认 → 批量执行

1. 向用户呈现报告摘要 + 建议数量分布
2. 询问用户：
   - 按严重级别批量确认（"确认 P0+P1，P2 忽略"）
   - 或逐条确认（列表编号，用户回复编号）
3. 按确认范围执行批量修改
4. 修改后执行终致性检查（quick scan 确认没有格式化破损或替换遗漏）

---

### Phase 5（可选）：终致性检查

用户确认修改后，快速扫描改后文档：
- 确认标记/占位符没有被遗漏
- 确认格式保持完整（代码块、标题、列表）
- 确认没有因替换引入新错

---

## 问题严重性分级

| 级别 | 标签 | 含义 |
|------|------|------|
| 🔴 P0 | 严重错误 | 事实错误或严重误导，不改会导致读者产生错误认知或生产事故 |
| 🟡 P1 | 重要优化 | 重要遗漏、不严谨表述、术语不统一，影响可信度或可操作性 |
| 🟢 P2 | 轻微建议 | 表述优化或锦上添花，不改不影响正确性 |

---

## 硬规则

1. **必须**在 Phase 1 同时派发 4 个 Agent，不得串行。
2. 每个 Agent **必须**独立读取完整文档，不得相互引用或等待。
3. **不得**在 Phase 3 之前向用户展示任何发现。
4. 聚合时**必须**去重，避免同一问题被多个 Agent 报告后重复展示。
5. **不得**在用户确认前修改原文。
6. P0 问题必须在报告开头突出显示。
7. 无发现的 Agent 输出"本维度未发现问题"而非预留空位。
8. 审校报告**必须**写入独立文件，不得仅在对话中展示。
