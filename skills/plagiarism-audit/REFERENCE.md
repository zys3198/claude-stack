# Plagiarism Audit — 参考

## 1. 来源抓取重试命令

### GitHub Markdown（中文路径）
```bash
# 试 1：URL 编码 raw
curl -s "https://raw.githubusercontent.com/<owner>/<repo>/<branch>/$(python3 -c "import urllib.parse,sys; print(urllib.parse.quote(sys.argv[1]))" "第二部分-核心系统篇/06-记忆系统.md")"

# 试 2：gh api 拿直链
gh api "repos/<owner>/<repo>/contents/<中文路径>" --jq .download_url | xargs curl -s

# 试 3：gh api 直取正文
gh api "repos/<owner>/<repo>/contents/<中文路径>" -H "Accept: application/vnd.github.raw"
```

### 公众号 / 普通网页
- webReader / WebFetch 原始 URL
- 失败 → WebSearch `"<文章标题>"` 找转载/缓存
- 公众号图多，抓回后正则剥 `<img>`/CSS 噪声，只留正文

### 失败判定
四种方式（原 URL / raw / gh api / 搜索）全部拿不到正文，才能标"无法获取"。标之前再 WebSearch 一次确认无缓存。

## 2. 原创元素提取清单

来源到手后，逐类摘出受保护元素（写进评判员 prompt）：

| 类别 | 例 |
|------|-----|
| 原创举例组合 | 特定的错误示例组合（如"会话流水账+代码统计+活动日志"三段） |
| 原创比喻 | "金鱼记忆""垃圾桶""工位便签"等 |
| 原创金句 | 可复述但不该同义搬运的判断句（如"只记代码推不出来的东西"） |
| 原创论述框架 | 特定的原则命名+排列（如四条设计原则的固定顺序） |
| 原创句式封装 | "X一致Y可变""两个坑：A和B"等对仗结构 |
| 原创数字/例子 | 特定举例（"0.87 相似度""周四→2026-03-05"） |

## 3. 评判员 prompt 模板

逐句评判员（查 A1/A2）和骨架评判员（查 A3/B2）各派。模板分两版。

### 3a. 逐句评判员（查 A1 逐字 / A2 洗稿）

```
你是独立反抄袭评判员。任务：逐句比对文章与来源，找逐字抄袭/洗稿改写。

## 允许（不算抄）
- 官方文档原话、源码常量/函数名/提示词原文
- 技术名词、机制名、API 名
- 固定结构模板（如 Why/How to apply）
- 技术事实（机制本身的客观描述）
- 通用思路、标准算法原理、语言语法

## 必改（算抄）
- A1 逐字复制：原封不动或只改极少数词的大段搬运
- A2 洗稿改写：同义词替换/调句序/合并多源，逐句可对齐
- 原创举例组合、原创比喻、原创金句句式
- 原创论述框架、原创句式封装（"X一致Y可变"等对仗）

## 文章
<路径，用 Read 读>

## 来源原创元素清单
<粘贴本来源的元素清单>

## 输出
逐条：行号: [文章句] ≈ [来源句] | 类型: A1逐字/A2洗稿/允许 | 是否核心区(核心/边缘) | 理由
最后总判 PASS（全清）或 FAIL（列必改）。
严格但合理：技术事实不算抄，同义改写算残留。别放过，也别冤枉。
```

### 3b. 骨架评判员（查 A3 神似 / B2 架构克隆）——逐句评判员必漏，单独派

```
你是独立反抄袭骨架评判员。任务：不只看词面，比文章与来源的"骨"——章节顺序、论证路径、分析视角、独特举例组合、模块切分。这是最致命也最易漏的侵权类型。

## 抓什么（算抄）
- A3 骨架神似：文章的章节顺序、每节论证路径、独特视角，与来源高度雷同，即便文字全不同。"换皮不换骨"=换词但保留原叙事结构。
- B2 架构克隆（代码）：模块划分/接口设计/核心逻辑映射高度相似，即便无逐字复制。
- 独特举例组合照搬：来源用"流水账+代码统计+活动日志"三段举例，文章用同组合换措辞=照搬。

## 不抓什么（不算）
- 通用叙事顺序（如"先讲问题再讲方案"是常识，不算骨架）
- 技术机制本身决定的讲述顺序（如讲 RAG 必先讲 embedding，不算）
- 通用思路、标准算法原理

## 文章
<路径，用 Read 读>

## 来源骨架指纹
章节顺序: <来源 1→2→3 节序>
论证路径: <每节怎么论证>
独特视角: <来源的分析角度>
模块切分(代码): <若有>

## 输出
先列文章骨架（章节序+路径+视角），再逐维比来源：
[维度]: 文章=<> / 来源=<> | 类型: A3神似/B2克隆/通用顺序 | 是否核心区 | 理由
最后总判骨架 PASS（独立结构）或 FAIL（换皮不换骨，需打散重排）。
宁可严：骨架神似比逐句抄更致命，换词救不了，必须换骨。
```

骨架评判员输入需 plan 生成者提供"来源骨架指纹"（见 SKILL.md Step 1）。

## 4. 姐妹段检查（改前必做）

同一论点/例子常出现多处。改前按关键词 grep 全部位置：

```bash
grep -n "关键词" <文章>
```

典型姐妹段组合：
- feedback 例子：正文论述段 + frontmatter 代码块 + 四类型表格 + 检索示例代码块
- 时间换算：正文例子 + 误区表格 + 展开说
- 设计原则：正文原则条 + 对比表格 + 误区

改一处必须同步所有姐妹段，否则下一轮评判员必抓。

## 5. 技术事实 vs 措辞搬运（人工兜底）

评判员常把技术事实描述也判残留。遇到时人工复核：

| 是技术事实（保留） | 是措辞搬运（改） |
|--------------------|-------------------|
| JSONL "追加写/读后清空"（机制本身） | 给机制贴的原创标签（如"读后即焚"） |
| 缓存命中省钱（客观效果） | 具体算账叙事框架（"80000 token 降一个数量级"） |
| 模型分档筛选（事实） | "为什么是 X 不是 Y"+原创三连论证 |
| 跳过节流计数（机制） | "已完成的工作不该被节流延迟"价值判断句 |

判定为技术事实 → 保留或仅微调措辞。判定为措辞搬运 → 换切入角度重写。

## 6. 接入 multi-review-pipeline

multi-review-pipeline Step 2 派 4 个固定 reviewer。当用户在调用时**提供了外部来源**（URL/文件/粘贴），自动加派第 5 个 reviewer，prompt 用本 skill 的评判员模板，subagent_type 用 general-purpose。

来源判定：用户消息里出现 `http`/`来源`/`参考`/`对照`/`原文` + 文章路径，即视为有来源，触发第 5 个 reviewer。无来源时不触发，保持原 4 reviewer。
