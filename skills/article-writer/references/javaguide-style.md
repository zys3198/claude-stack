## §6 风格模式：JavaGuide AI 系列

**当用户指定 JavaGuide 模式时，应用本节全部规范。覆盖默认模式的对应条款。**

### 6.0 核心写作原则：理解后重新创作

**最高优先级规则。** 格式、结构、语气——一切规范在它面前都让路。

**正确的流程四步：**
1. **完整理解**：通读参考资料，直到能脱稿向同事讲清楚
2. **提取要素**：抓住核心观点、逻辑链条——不是抓原句
3. **忘掉原句**：合上参考资料。脑子里只剩"我想说什么"
4. **重新讲一遍**：用自己的语言写。像给朋友解释一样

**自检**：随便挑一段对照参考资料。句子层面找不到逐句对应关系但观点逻辑一致→过。能逐句对齐只是换了词→不过，重来。

**参考资料与版权边界：**

不算侵权：技术名词、代码示例/API调用/配置片段、官方定义原话引用（注明出处）、架构图/流程图结构、YAML/JSON固定格式

算侵权/洗稿：对概念的个人理解方式和解释路径、非官方的个人原创例子和场景、个人见解/评价/态度、行文节奏和叙述顺序、文章开头钩子和收尾

**核心判断**：技术事实只有一个，但**叙述方式可以不同**。先消化，再按规范写。

### 6.1 文章整体结构

```
YAML Frontmatter
→ 开头钩子（个人经历/痛点/真实场景，1-3段）
→ "这篇文章讲什么"导航列表（编号+字数）
→ 核心内容（## / ### 层级）
→ 自然收尾（可选，不需要单独的"总结"章节）
→ 参考资料列表（如有）
```

**YAML Frontmatter：**
```yaml
---
title: 文章标题（直击主题，可用冒号分隔，可用疑问句）
description: 一句话概述，含核心关键词，80-120字
category: AI 应用开发
head:
  - - meta
    - name: keywords
      content: 关键词1,关键词2,关键词3（5-10个）
---
```

**title 规范**：不要"详解""深入""一文搞懂"等修饰词。

**description 规范**：含核心关键词，概述覆盖的子主题。

**开头钩子** — AI 系列最鲜明的特征。四种模式：

| 模式 | 说明 |
|------|------|
| A 个人经历/踩坑故事 | 最常用 |
| B 常见误区/反直觉现象 | 纠正常见误解 |
| C 读者常见困惑 | 代读者提问 |
| D 行业观察/变化 | 从宏观切入 |

**导航列表**按文章功能选择。长教程、知识库和系列文章可以在开头加入；工具体验、开源项目分享和个人复盘默认直接进入正文。不强制写字数、"建议收藏"或 5-7 条固定要点。

### 6.2 语气与行文风格

**像一个有经验的开发者在跟你聊天**——有观点、不端着、敢说"我觉得"。

| 特征 | 说明 |
|------|------|
| 第一人称 | 用“我”“我们”“Guide”“小G”（小G 是 docs/ai 系列作者自称，给建议时“小G 的建议是”比“我建议你”少说教，可贯穿全文） |
| 直接评价 | 不怕说某个东西不好 |
| 口语叙事 | 用讲故事方式解释技术 |
| 自曝踩坑 | 亲身经历增加可信度 |
| 读者对话 | 直接用"你"对话读者 |
| ai-coding 开场 | 实战系列开头固定"你好，我是小 G/大家好，我是 Guide"打招呼，再接读者催更/互动或个人体验叙事 |

**开头选择**：从作者正在处理的具体问题、真实踩坑、反常现象、读者困惑或项目发现中选一种。优先写动作、失败和后果，尽快进入正文。

不要强制制造“先立误解、再翻转”。如果事实本身已经有张力，直接写事实；不要用“今天我们学 X”或空泛趋势铺垫代替开头。

**生活化比喻**：只在能解释内部机制时使用。优先给出真实对象、输入输出和处理过程；删掉比喻后读者仍能理解，就删。不追求每节一个或整篇固定密度。

**亲历实测段范式（原理/工具介绍型必备，不是一句“我踩过坑”带过）：**

介绍完一个原理或工具后，紧接着给一段“我拿它做了 X”的完整叙事：挑战（解决什么）+ 脑洞（想到的反常规/巧妙操作）+ 过程（怎么一步步实现，截图/核心 Prompt）+ 结果（产出什么）。一句“我踩过坑”不够，要把决策点摊开。实例：
- 「我用 grilling 确认了一次知识库面试需求」--问了三个决定：知识库角色、单库多库、入口，每个的取舍都写清
- 「我面试平台跨模块任务，单 Agent 跑到中途上下文撑爆，改 Sub-agent 并行才完成」

**适用边界范式（收尾前给“什么时候不该用”，反向克制比硬推可信）：**

工具或原理讲完，补一段“什么时候不该用/不必用”--小任务手动更快、纯风格问题 lint 够了、没 X 基础嫌麻烦。实例：
- 「改一处文案、补一个空值判断，直接做通常更省时间」
- 「Claude Code 用得稳，就没必要为了换工具而换工具」

**血泪教训式警示句范式**：讲完一个坑后，用一句简短凌厉的警示句结晶教训，独立成段或段首。比亲历实测段更短（一句非叙事），比适用边界更尖锐（教训而非克制）。模板：「血泪教训：别指望 X——[具体触发条件]，[具体后果]」或「很多团队栽得最多的是：把 X 当成 Y」。

**故意打破范式**：论述中故意加口语打断，破坏过度严谨，制造活人感。3 种：① 重复强调（“就是…就是…就是单纯的想看看”，三连加强口语）；② 中途模糊（“某个免费的国产模型，我就不说是谁了”，像跟朋友聊天）；③ 省略打断（“我寻思了一下我没寻思明白”，语法不完整但真实）。适用边界：博客/面经/ai-coding 实战系列可用；知识库/面试题/论文摘要不用，会损严谨性。

**口语化词汇**（适度使用而非均匀分布）：放转折/降预期/预判疑问等功能位置，不随机撒。
- 高频：说白了就是、搞懂、坑、踩坑、很稳/不稳
- 适中：翻车、扛住、接住、跑偏、白搭、够用、硬扛
- ai-coding 系列更重：真香、爆肝、屎山代码、一把梭、牛头不对马嘴、一本正经地胡说八道
- 低频：玄/很玄

### 6.3 内容组织模式

**概念拆解型**（MCP/RAG/Agent Skills 等）：
```
是什么？→ 为什么需要？→ 和相近概念的边界 → 核心原理/架构 → 怎么落地
（落地到 Java 技术栈时，补「Java 后端怎么落地 X」四件套：模块拆分清单 + 核心表设计 + 核心接口定义 + 最小请求链路，每块前后配中文说明职责）
```

**系统工程/链路拆解型**（RAG 优化/AI 应用架构）：
```
问题场景 → 全景图(Mermaid) → 环节逐个拆解 → 排查路径
```

**实操指南型**（Spec Coding/Codex）：
```
开场故事 → 核心理念 → 对比 → 具体步骤 → 常见坑 → 工具清单
```

**面试题型**（AI 面试题系列）：
```
### ⭐️ 问题标题
简短回答 + 展开解释 + 代码/架构图补充
```

**实战案例型**（ai-coding/cases 系列）：
`
打招呼+选模型背景 → 环境配置（截图步骤）→ 场景一/场景二（背景→需求→方案→编码→验收）→ 实战总结（AI能做什么/注意事项/使用建议）→ 写在最后
`
特征：场景驱动，每个场景是独立闭环。代码穿插在编码环节但前后必配口语说明。

**工具实践型**（ai-coding/practices 系列）：
`
开场故事/个人体验 → 核心理念 → 具体建议（每条配正反例）→ 按风险分层使用 → 常见失败模式 → 常用命令/工作流清单 → 总结
`
特征：建议清单驱动，按风险高低分层（小任务/中等任务/高风险任务）。截图用于配置步骤和读者互动。

**逐一展示+升番（测评/工具对比文）**：多产品/案例对比时不平铺清单或纯表格，逐个带情绪标签/吐槽展示，按“最弱 -> 最强”升番（每个比上个更炸），让情绪曲线层层推高。表格给参数，逐一展示给体验+情绪，两者互补。

**面试 Q&A 收尾**：仅在目标读者确实需要自测或 SEO 时追加「## 面试问题」章节。工具分享、项目体验和工程复盘默认不加；若追加，每道题必须引入正文没有的新判断，不能把正文改造成同构问答。
### 6.4 格式元素规范

**代码块**：语言标注必填。AI 系列特有类型：`text`（Prompts）、`json`（API 响应）、`yaml`（配置）、`mermaid`（流程图）。

**源码/参数处理四原则（跨子系列统一约束）：**

1. **表格为默认论证载体，代码密度远低于表格。** 对比表/参数表/场景表三件套承担清单化呈现决策维度的工作。实例：llm-gateway 760 行 134 处表格行 vs 16 个代码块；rag-optimization 694 行 53 处表格行 vs 10 个代码块。
2. **代码只放带中文注释的关键片段，绝不裸贴大段实现。** 每个代码块前后必有口语解释——先说这段在干什么，贴代码，再说为什么这么写。实例：pgvector 查询带行内注释 `-- <=> 是余弦距离运算符(0 = 完全相同, 2 = 完全相反)`；structured-output 用「坏设计/好设计」成对片段而非完整类。
3. **大段实现源码放末尾独立章节，不在正文散落。** 实例：workflow-graph-loop 把完整 Spring AI Java 实现放进独立 `## 代码实现` 专节，按「第一步/第二步/第三步」分步骤组织，每步配中文说明。
4. **复杂逻辑用 Mermaid 流程图表达而非源码。** 实例：知识更新的「源系统→变更检测→队列→处理→去重→Embedding→三端写入」全链路用 Mermaid 而非代码。
**边界**：接口定义/record/枚举/表 DDL 是工程契约非实现源码，可用于说明分层与职责，不适用「绝不裸贴大段实现」；但仍需前后配中文说明其职责，不裸贴。

**表格**：最常见三种——对比/差异表、层级/职责表、问题诊断表。首列加粗。

**Blockquote**：三种用途——官方文档引用（英文原文+中文翻译）、"说明一下"补充说明、扩展阅读/前置知识提示。

**Mermaid**：大量使用。`flowchart LR`（横向）或 `flowchart TB`（纵向）。统一配色：client 青色、gateway 紫色、business 橙色、infra 紫色、storage 蓝色。

**配图三种方式（按子系列选择）**：
- 预制图（docs/ai 概念系列主力）：上传到 oss.javaguide.cn，正文用 ``![图名](https://oss.javaguide.cn/...)`` 引用 SVG/PNG。文件名语义化英文（如 ``mcp-four-layer-architecture.png``）。单篇常 8-15 张，agent 概念组几乎全用预制图不用 Mermaid。
- Mermaid 代码图（RAG/系统工程系列主力）：正文直接写 ```` ```mermaid ```` 围栏。配色固定复用（见上方）。
- 截图（ai-coding 系列主力）：配置步骤截图、读者互动截图、效果验证截图。用于实操环节而非概念讲解。

**交叉引用**：织入正文叙述而非单独"相关阅读"区块。三种模式——正文中自然引出、前置知识条件、系列导航。

### 6.5 内容质量要求

- 标注时效：引用具体日期（"截至 2025-06-18"），不用"当前""最新"
- 量化工程感：拿具体数据说话，不泛泛说"性能更好"
- 观点有理由支撑
- 参考资料格式：官方文档放最前面，不放低质量转载
- 工具、CLI、模型和评测数据绑定版本、日期或运行环境
- 区分官方文档、源码当前实现、作者亲自实测和个人推论，不把四类信息混写成一个确定事实
- 介绍功能时写清输入、处理、输出和失败行为
- 涉及 fallback、去重、缓存、权限或安全隔离时，说明判定依据和不保证的边界

### 6.6 标题层级

- `##`：一级章节，`###`：二级章节，`####`：三级（极少用）
- 概念定义用疑问句、关系对比用疑问句、**过程/选择/方法类也用疑问句**（"stdio 和 Streamable HTTP 怎么选？""各范式怎么选？""怎么落地？"）。第三类实际文章里高频出现，不要只用陈述句。
- ⭐️ 标记重点章节：核心章节用 ## ⭐️ 标记（如"## ⭐️SKILL.md 到底怎么写？""## ⭐️ 怎样把 JSON 从格式要求变成工程契约？"），用于引导读者优先阅读
- 口语化句式贯穿标题：「到底」「到底有什么区别」「能不能」「是什么关系」可反复使用
- AI 系列**不使用**数字前缀（如 ``## 1 背景``）

### 6.10 AI 辅助创作工作流（人机协作边界）

2026 年纯人工创作是过时命题——查资料、找灵感、校对、做封面，AI 渗透每个环节。关键不是“用不用 AI”，是“关键决策点是不是人在做”。

**AI 适合加速的三个流程：**
- **找证据写观点**：让 AI 给 5 个能证明 + 5 个能反驳观点的案例，自己判断挑选。“AI 找弹药，开枪方向我选”
- **找类比和比喻**：AI 生成候选，自己挑和改。烂候选一眼能看出是 AI（太工整、太对仗、太正确）
- **定好角度和框架后的扩写**：方向、骨架定了，让 AI 填肉，质量高且快

**AI 做不到的（神之一手）：**
关键角度的跨领域概念嫁接（如疲惫时目光扫过书脊，从淘宝 9.9 元商品跳到科幻小说的社会分层）、真实瞬间的情绪反应——任何 prompt 复现不了，独属于人。实测/体验/评测类内容同理，必须自己用、自己踩坑，AI 替代不了亲历（首发连网上参考都没有时尤其如此）。

**核心判断：** “这篇文章是不是人写的”是过时问题。真正的问题是：有没有一个真实的人在做判断、做情感表达？在 AI 给五个平庸候选时说“不对，这些都太普通了”自己想；在关键瞬间是真的鼻子一酸，不是表演。

**幻觉处理：** 生成时不强抑制幻觉（创意前提），但产出后用精准模型（如 GPT-5 Thinking）核查事实不符。§1“不编造”约束最终产出，不抑制生成期创意。

**AI 初稿 vs 人改 before/after**：展示“AI 稿 -> 人改”的具体句对，给修改一个可对照范式。3 类方向：① 工具名精确化（AI“Midjourney 他玩得溜” -> 人“Deepresearch/Claude code/Clawbot 第一时间扑上去”，用当下具体名）；② 虚构场景 -> 真实场景（AI“有一次我需要批量处理图片” -> 人“就像我今天正在搞的爬全网数据统计到飞书多维表格”）；③ 数字精确化 + 个人判断（AI“每天工作六小时” -> 人“每天 2 小时” + 加“我真的觉得”）。

### 6.11 JavaGuide 模式降 AI 检测：改写守则

> **定位**：本节约束 JavaGuide 模式**改写已有素材**时的降 AI 检测操作；用户要求降检测时，本节优先于 §6.1/§6.3/§6.6。
> **核心认知**：低 AI 检测来自**平铺体**——平铺散文 + 裸命令 + 名词短语标题；高检测来自「AI 教程腔装饰」与「结构脚手架」（Q&A 章、导航列表、编号结尾、代码围栏、`###` 层级）双叠加。降检测场景切换平铺体，不是在完整教程体上微调。
> **两种 JavaGuide 文体**：① 公众号原始文体（平铺、无 Q&A/导航/编号）→ 降检测场景用；② docs/ai 教程文体（导航/Q&A/表格/围栏）→ 默认 JavaGuide 场景用。降检测场景按 R1-R16 收敛。

**R1 元叙述过渡删除**：删"先说背景，不长""背景交代完。下面进入正题""还有一件事必须先说清楚""最后提醒一个配置边界"等自报流程句。
- 为什么：原文此类句零出现；改写版每个衔接点都加，检测器判为教程腔信号。
- 正例：直接进内容——"准备 DeepSeek API Key"后直接"先到 DeepSeek 开放平台创建一个 API Key。"
- 反例："先说背景，不长。DeepSeek V4 Flash 正式版前几天上线…"

**R2 正文设问改陈述**：删正文自问自答（"为什么要写这个？…另一个是我自己的体感""配置完怎么确认？这里有个反例必须先说"），直给信息。
- 为什么：设问是模板化 Q&A 桥；原文平铺直叙给信息。标题问句不受此限（见 R6）。
- 正例："调用 `deepseek-v4-flash` 时，只要在请求参数里声明 `web_search` 工具，就能用 DeepSeek 服务端的搜索。"
- 反例："配置完怎么确认？这里有个反例必须先说。"

**R3 类比克制**：类比先过三步判断——① 是否解释内部机制（不是表面印象）；② 是否一句内完成；③ 删掉后读者能否从上下文回想到真实理解。三问不过就删。
- 为什么：原文几乎零类比；改写版"这就像装驱动""货架上摆着商品…过了收银台"是装饰性类比，还打断叙述节奏。
- 正例：MCP = "USB-C 接口"（机制型、一句）保留。
- 反例："打个比方。货架上摆着商品，不代表你能直接买走。要能结账，得先过了收银台。对 OMP 来说，'收银台'就是两道检查…"——删。

**R4 句中加粗默认不加**：正文句中加粗全篇 ≤3 处、每处 ≤12 字，仅用于最关键警告。
- 为什么：原文零加粗，高频加粗是 AI 排版特征。
- 正例：不靠加粗，靠语义和位置自然凸显。
- 反例："还有一件事必须先说清楚：**两个配置目录不能混**。"

**R5 口语强词收敛**："血泪教训""千万别""必须说清楚""务必"等强词，每种全篇 ≤1 次。
- 为什么：强词留给唯一情绪高点，重复即模板腔。
- 正例：全篇保留一处"血泪教训"，其余换平实警告。
- 反例："血泪教训：…""这里有个坑必须提醒：…"多处强词连用。

**R6 小标题名词短语 ≥70%**：`##`/`###` 标题名词短语占 ≥70%（"准备 DeepSeek API Key""安装 OMP""查询并选择模型"），问句/祈使句 ≤2 个。
- 为什么：原文全名词短语；改写版问句标题 + 祈使标题密集。§6.6 问句条款用于概念定义/对比关系，不用于操作步骤。
- 正例："### 装 OMP：四条路选一条""### modelRoles 默认模型记在哪"
- 反例："### 上一篇的悬念，在这里解开""记住分工：…"

**R7 命令裸写**：操作句去"就行/只需/别急着/不用再"等壳词，命令直给。
- 为什么：原文"先到 DeepSeek 开放平台创建一个 API Key""不要用 echo $DEEPSEEK_API_KEY 检查"是裸命令；改写版壳词堆叠。
- 正例："先到 DeepSeek 开放平台创建一个 API Key。"
- 反例："去 DeepSeek 开放平台创建一个 API Key 就行，网址在文末参考资料里。"

**R8 结构自述删除**：删"这篇全文接近 5000 字，主要看这几块""先说清楚这篇的材料边界"等自述句；导航列表本身可留，但删"全文接近 X 字"固定元素、不用模板原句，要点直接写具体信息。
- 为什么：改写版自述密度高；原文用"这篇把 OMP 和 Pi 的配置、模型切换和验证过程完整记录下来"自然衔接。
- 正例："这篇把 OMP 和 Pi 的配置、模型切换和验证过程完整记录下来。"
- 反例："这篇全文接近 5000 字，主要看这几块。1. … 7. …"

**R9 新增章节去模板化**：Q&A 章 ≤5 题、题型错开（定义/流程/对比/坑各一），"展开"必须补正文没有的新判断。**降检测场景整章删除，见 R12。**
- 为什么：改写版 Q1-Q5 全同构（问句+简答+展开），模板味重；原文没有 Q&A 章。§6.3 Q&A 收尾在降检测场景收敛为 ≤5 题。
- 正例：题目题型错开，展开给具体参数或决策依据。
- 反例：五个"为什么/什么时候"式题目 + 统一"简答/展开"模板。

**R10 转折二分壳收敛**："不过/但是"开头的二分壳（"榜单是参考，不是结论"）每 500 字 ≤1 个。
- 为什么：改写版"不过基准归基准""但这里有个容易误会的点"密集；原文一次转折自然带过。
- 正例："榜单数据不能直接代表所有项目里的实际效果，不过从我最近看到的反馈来看…"（一次）。
- 反例："不过基准归基准。…这点要冷静。…但从我最近看到的反馈来说…"

**R11 篇幅不均**：最长节 ≥ 最短节 ×3；不为结构完整均匀铺排过渡节。
- 为什么：原文内容集中在主体（自然不均匀）；改写版平均摊成 8 节，均匀度被检测器加分。
- 正例：原文比例——开头 23% / 主体 74% / 收尾 2%。
- 反例：改写版最大节 31.47% vs 最小节 6.71%。

**R12 Q&A 章整章删除（降检测场景）**：删除 `## 面试问题` 整章，不保留"收敛版"。
- 为什么：参考原文无 Q&A 章；`**Q：** 简答：… 展开：…` 格式本身是 AI 面试模板味，题型错开救不回来。
- 正例：删除后，面试相关事实保留在正文对应节。
- 反例：保留 5 题但"题型错开 + 展开补新判断"——仍高。

**R13 导航列表删除（降检测场景）**：删除开头"分这几块 / 主要看这几块"导航列表，一句话承诺后直接平铺进正文。
- 为什么：参考原文无导航列表，开头直接平铺进正文。
- 正例："这篇把 OMP 和 Pi 的配置、模型切换和验证过程完整记录下来。"（一句话承诺，无列表）
- 反例：导航列表 1-7 条。

**R14 结尾禁用编号清单**：收尾用平铺行动邀请，不用"三点 / 几点"编号复述。
- 为什么：参考原文以行动邀请收尾。`style-craft.md` §2.8 编号判断清单在降检测场景收敛为平铺。
- 正例："这篇先把接入过程记录到这里。感兴趣的朋友，可以用同一份编码任务分别跑一遍 OMP 和 Pi…"
- 反例："接入过程就这些，三个要点再拎一下：1. … 2. … 3. …"

**R15 代码命令裸写**：命令不包围栏，直接平铺文本行（多行命令逐行写出）。
- 为什么：参考原文命令全部裸写。围栏是"越规整越像 AI"的直接来源。
- 正例："omp models deepseek" 裸行。
- 反例：```bash 围栏包命令。

**R16 警示标签删除**："血泪教训：""切记""务必"标签删掉，改平铺警示句直陈。
- 为什么：标签壳比警告内容更被罚。R5 允许的"每种 ≤1 处保留"在此失效——单独 1 处仍拖高整段。
- 正例："不要用 echo $DEEPSEEK_API_KEY 检查，这会把完整密钥直接打印到终端，截图时很容易一起带出去。"
- 反例："血泪教训：环境变量里的是密钥，不是普通配置。任何会把内容打印到屏幕的检查方式，都别用。"
