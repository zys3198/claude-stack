# 综合提炼：两子系列差异 + 现有 §6 增量建议

> 调研时间：2026-06-27
> 数据源：01-concept-series.md（docs/ai 8 篇）+ 02-practice-series.md（docs/ai-coding 7 篇）
> 对照基准：article-writer SKILL.md §6 现有内容

## 一、两子系列核心差异总表

| 维度 | docs/ai 概念系列 | docs/ai-coding 实战系列 |
|------|-----------------|----------------------|
| **核心使命** | 讲清"是什么/为什么不是你想的那样" | 讲清"怎么做/什么场景用哪一层" |
| **说理骨架** | 误区破题（很多人以为 X，其实 Y）正面讲原理 | 误区破题 + 反转句式，反面破误区 |
| **开头签名** | 个人经历/踩坑 + 导航列表（字数+要点） | 打招呼 + 读者反馈截图/真香反转 |
| **自称** | "我"/"Guide"/"G 友"混用 | cases="Guide/笔者"，practices="小 G"（稳定分化） |
| **比喻密度** | 高（每千字 1-2 个，每概念配锚定比喻） | 低（集中在破题段，正文实操段不用） |
| **主力格式** | 预制图（oss.javaguide.cn）+ 表格 | 截图（配置/效果/读者互动）+ 代码块 + 命令清单 |
| **Mermaid** | 仅 rag-optimization 密集用（统一配色） | 0 Mermaid，用 drawio/svg 代替 |
| **⭐️ 标记** | 仅 skills 用（个别现象） | 0 次（7 篇全无） |
| **结尾模式** | 回扣误区 + 给最小可行路径 | cases="写在最后"+参考资料；practices=总结+回扣核心理念 |
| **分层结构** | 按概念层级（是什么→为什么→怎么落地） | 按风险/规模分层（小/中/大任务，贵/便宜模型） |
| **社交证明** | 无 | practices 独有读者催更/评论/阅读量截图 |
| **模板/清单** | 落地检查清单 | 命令清单 + Spec 模板 + 踩坑清单（可复制） |

**一句话区分**：
- 概念系列 = **老司机面对面给你讲清楚一个技术概念**
- 实战系列 cases = **实战报告**（"我做了 X，结果 Y"）
- 实战系列 practices = **经验手册**（"我建议你这样做 X"）

## 二、现有 §6 勘误清单（写错的，必改）

### 勘误 1：§6.2 ai-coding 口语化词汇清单严重失实

**现有写法**：
> ai-coding 系列更重：真香、爆肝、屎山代码、一把梭、牛头不对马嘴、一本正经地胡说八道

**实测真相**（7 篇实战系列扫描）：
| 词 | 现有定位 | 实测出现次数 |
|----|---------|------------|
| 一把梭 | ai-coding 高频 | **0 次** |
| 牛头不对马嘴 | ai-coding 高频 | **0 次** |
| 一本正经地胡说八道 | ai-coding 高频 | **0 次**（deepseek 篇有近似意象"看起来还挺像那么回事"） |
| 屎山代码 | ai-coding 高频 | **仅 1 次**（spec-coding 对话开头） |
| 真香 | ai-coding 高频 | 2 次 |
| 爆肝 | ai-coding 高频 | 2 次 |

**应改为的实战系列真正高频词**（按跨篇频率）：
- **干活 / 干起活来**（4+ 篇）—— "V4-Pro 干起活来到底怎么样"
- **翻车**（3 篇）—— "翻车情况也越来越多"
- **兜底 / 兜得住**（4+ 篇）—— "失败了怎么兜底"
- **跑起来 / 跑得起来**（5+ 篇）—— "代码看起来能跑"
- **劝退**（2 篇）—— "不然你会先被文档劝退"

**修正方向**：把"一把梭/牛头不对马嘴/一本正经地胡说八道"从 ai-coding 词表删除（它们是概念系列词或纯臆造），换成实测高频的"干活/翻车/兜底/跑起来"。真香/爆肝/屎山代码保留但降级为"个别现象（1-2 次）"。

### 勘误 2：§6.2 ai-coding 开场自称描述不准

**现有写法**：
> ai-coding 开场 实战系列开头固定"你好，我是小 G/大家好，我是 Guide"打招呼

**实测真相**：自称按子系列稳定分化，不是随机混用：
- **cases 系列**：`大家好，我是 Guide` / 第三人称 `Guide` / `笔者`（偏正式，建客观记录感）
- **practices 系列**：统一 `你好，我是小 G`（4/4 篇，建个人权威感）

**修正方向**：明确写出自称分化规则，让 AI 写 cases 时用"Guide/笔者"、写 practices 时用"小 G"。

### 勘误 3：§6.6 ⭐️ 标记被当成通用规则

**现有写法**：
> ⭐️ 标记重点章节：核心章节用 ## ⭐️ 标记

**实测真相**：
- 概念系列 8 篇：仅 skills 1 篇用 ⭐️
- 实战系列 7 篇：0 次

**修正方向**：⭐️ 标记降级为"可选，仅用于超长文（>8000 字）且概念密度高的篇章，标注最核心 2-3 个章节"，不作通用要求。

### 勘误 4：§6.4 Mermaid 配色被当成全系列统一

**现有写法**：
> Mermaid：大量使用...统一配色：client 青色、gateway 紫色...

**实测真相**：
- 仅 rag-optimization 密集用 Mermaid（4 个 flowchart，有配色体系）
- 实战系列 7 篇 0 个 Mermaid，用 drawio/svg 代替
- 其他概念篇 Mermaid 0-1 个

**修正方向**：Mermaid 定位为"系统工程/全链路拆解型专用（如 rag-optimization），其他类型用预制图或 drawio/svg"。配色体系保留但标注适用范围。

## 三、现有 §6 缺失清单（没写的，必补）

### 缺失 1：cases vs practices 子系列内部差异（最重要）

现有 §6.3 只笼统列了"实战案例型/工具实践型"两类模板，但没有细化**自称分化、截图用法分类、结尾差异、时态差异**。

应补一张完整的 cases vs practices 差异表（见上方第一部分总表 + 02-practice-series.md §6.9），让 AI 能精准区分写哪种。

### 缺失 2：读者互动截图（practices 签名社交证明）

现有 §6.4 配图三种方式只提了"截图（ai-coding 系列主力）：配置步骤截图、读者互动截图、效果验证截图"。

但没有强调**读者催更/评论/阅读量截图是 practices 系列的签名手法**，用于建立社交证明。spec-coding 开头贴读者催更截图、the-cool-tricks 贴读者评论、claudecode-tips 炫阅读量 6w+——这是 practices 区别于 cases 和概念系列的关键。

### 缺失 3：实战系列"按风险/规模分层"签名结构

practices 系列几乎每篇都有分层结构：
- spec-coding 按"10 模块以内/10-30/30+"
- the-cool-tricks 按"贵模型 vs 便宜模型"
- claude-md-best-practices 按"CLAUDE.md vs rules vs Skills vs Hook"约束硬度

现有 §6 没有提炼这个"什么场景用哪一层"的分层签名。

### 缺失 4：命令清单/模板清单/踩坑清单（实战系列三件套）

practices 系列结尾附近固定有三件套：
1. **命令清单**（可复制命令，如 claudecode-tips 的"常用命令"三类）
2. **模板清单**（可直接用的模板，如 spec-coding 的三套 Spec 模板）
3. **踩坑清单/失败模式表**（症状+处理方式两列表）

现有 §6 只提了"工具清单"，没有细化这三件套。

### 缺失 5：概念系列"比喻锚定"模式

概念系列每个核心概念都配一个**会被反复回引的锚定比喻**：
- MCP = 接线规范/USB-C
- Context Engineering = 给厨师准备厨房
- Harness = CPU + OS
- RAG = 证据加工流水线
- Progressive Disclosure = 查书/到新城市给地图

这不是随机比喻，是"一个概念一个锚点，后文反复回引"的结构。现有 §6.2 只说"生活化比喻范式"密度，没有说"锚定"机制。

### 缺失 6：概念系列结尾"回扣误区 + 最小可行路径"模式

概念系列结尾不是"总结本文讲了什么"，而是：
1. 回扣开头的误区
2. 给一条"先做 X，再做 Y"的最小落地路径

如 context-engineering 结尾"先把 System Prompt 和工具边界写清楚；再把 RAG 检索做准"；rag-optimization 给 9 步落地优先级。现有 §6.8 结尾模式表没有这条。

### 缺失 7：开头钩子第五种模式（场景对话/剧本式）

现有 §6.1 开头钩子四模式（A 个人经历/B 误区/C 困惑/D 行业观察）。实测 llm-gateway 用了**面试官对话剧本式**开场（"面试官看了一眼我的 AI 项目架构图，突然停住了..."），效果最戏剧化，应补为第五种模式。

### 缺失 8：导航列表的"阅读契约"仪式感

概念系列 6/8 篇在开头第 3-5 段固定放"本文接近 X 字，主要看这几块：1. 2. 3."。这不只是导航，是"阅读契约"仪式。现有 §6.1 提了导航列表要素，但没强调它的"契约"属性和位置（第 3-5 段）。
