# Article Writer — 深度文章创作与优化

## 概述：两种模式

| 模式 | 触发条件 | 输出 |
|------|----------|------|
| **创作模式** | 无素材原文，只有主题 | 从零开始，基于主题深度创作 |
| **优化模式** | 有素材原文（文件路径/粘贴内容） | 深度改写优化，保留核心信息但重组织语言 |

## 概述：风格模式

请求中提及 JavaGuide 或 javaguide → **JavaGuide 模式**，应用 §6 全部规范。

未指定 → **默认模式**，按 §2-§5 通用低 AI 味写作。

---

## §1 核心原则（通用）

**三个底线：**
- 不洗稿：严禁直接摘抄或轻度替换原句，必须理解后重讲
- 不编造：没有来源支撑的经历、数据、路径、报错、实验结果不要硬补
- 不套模板：低 AI 味来自文体自然和细节真实，不来自固定开头、固定结尾、固定口头禅
- 不写干瘪：目标是准确、具体、有节奏
- 正文禁词："朴素"（尤其"技术栈比较朴素"）→ 改成具体构成
- 不配图：写作过程只产出文字、表格、代码示例。不生成 Mermaid/Draw.io/SVG/图片链接/配图占位
- caveman 输出纪律：分析、讨论、规划阶段保持 caveman 模式（省 token）；写文章正文（写入 .md 文件）时关闭 caveman，用完整自然中文

## §2 低 AI 味基础

### 2.1 低 AI 味真正来源

- **具体对象**：写清工具、系统、场景、约束
- **方法链条**："怎么做 → 为什么 → 效果"
- **真实细节**：参数、路径、阈值、模型、异常情况
- **取舍痕迹**：为什么选 A 不选 B
- **自然不均匀**：该长就长、该短就短

不要写成强制规则：
- 开头不一定要叠甲
- 不一定要第一人称
- 原理段不一定要插感受
- 口语不等于低 AI 味

### 2.2 开场模式

| 模式 | 适合文体 |
|------|---------|
| 对话/问答还原 | 技术面试文、概念辨析 |
| 具体痛点还原 | 工具介绍、教程 |
| 时间线故事 | 产品发布、复盘 |
| 直接设问式 | 知识库、面试题总结 |
| 功能/需求驱动式 | 工具推荐、产品发布 |

### 2.3 数字纪律

有具体值用具体值（"pass@1 从 80% 到 91%"）> 行为描述（"文件写入偶尔卡死"）> 不下抽象结论。

### 2.4 诚实标记

主动暴露局限和不确定。局限紧跟在优势之后，不单独开"不足"节。

### 2.5 节奏控制 & 口语词

长段推导后接极短短段。口语词放特定功能位置（简化解释/转折降预期/确认共识/预判疑问），不随机撒。

### 2.6 过渡连接

优先用口语过渡（"重点说说""接着就是"），匹配文体。知识库文直接靠问题标题衔接。

### 2.7 正反对比

教程文：反面示例（像读者会犯的错）+ 正面示例（具体到动作和结果）。

### 2.8 结尾模式

| 模式 | 适合文体 |
|------|---------|
| 个人期许式 | 产品发布、个人项目 |
| 开放判断式 | 工具推荐、趋势评论 |
| 经验互勉式 | 面经、个人经历 |
| 资源推荐式 | 知识库、技术教程 |

**不要在结尾处**：写"综上所述"、重复全文要点、升华到"AI时代的意义"。

## §3 按文体选择写法

### 3.1 博客/公众号/测评

使用者视角。"我最近在用 X，顺手聊聊 Y"。夸和吐槽都要具体。

### 3.2 技术方案/项目复盘

工程决策视角。先交代问题和约束，再写方案链条。多写"为什么这样设计"。

### 3.3 论文摘要/学术技术文

问题-方法-效果。开头直接说研究对象。方法具体到算法/数据结构/阈值/实验环境。语言正式但不宣传腔。

### 3.4 知识库/面试题总结

问答-递进。标题即问题。按认知递进排列（是什么→怎么用→为什么）。回答具体到版本号/参数。多用对比表格。

### 3.5 开源项目/工具推荐

痛点-替代-功能展开。极短段落密集推进。每个功能给具体参数。

### 3.6 面经/个人经历

时间线叙事。第一人称。关键节点给具体数据。失败经历不回避。

### 3.7 教程/实用指南

问题-方法-示例。每个建议配正面示例，关键建议配反面示例。

## §4 常见 AI 味信号

### 4.1 骨架层
- 标准模板：趋势铺垫→N点原因→N个方案→总结展望
- 章节过于均匀
- 段落同构模板：连续3段以上"观点句+解释+段尾总结"
- 段尾金句化收束
- 结尾"短期/长期/个人建议"三段式

### 4.2 句式层
- "不仅…而且…"、二分转折壳
- "说白了"后接复杂解释
- 口语词分布均匀如节拍器

### 4.3 词汇层

| AI 味词汇 | 替换方向 |
|-----------|---------|
| 综上所述、总而言之 | 直接删 |
| 赋能、打造、构建 | 说具体动作 |
| 核心机制、底层逻辑 | "这里怎么跑" |
| 显著提升、大幅优化 | 具体数字或删掉 |
| 值得一提的是 | 直接说那件事 |
| 朴素 | 改成具体构成 |

完整清单见 `references/ai-taste-blacklist.md`。

## §5 后处理

文章写入完成后依次执行：

1. **AI 味三遍扫描**（骨架→句式→词汇，见 §5.1）
2. 执行 `/humanizer`
3. 执行 `/chinese-markdown-normalizer`

### 5.1 AI 味三遍扫描

**第一遍：骨架扫描**。看各节篇幅是否均匀、开头是否趋势铺垫、段落是否同构、结尾是否三段式。优先删减合并，不做表层替换。

**第二遍：句式扫描**。逐段标出二分转折壳、"不仅…而且…"、"说白了"接复杂解释、箭头串流程等，重写。

**第三遍：词汇扫描**。查找 §4.3 词汇表，优先具体化。检查破折号（≤5 个/1500-3000字）、引号（非引用就去掉，反讽引号≤2处）。补充至少一处诚实局限表达。

**自检通过标准**：
1. 开头避开趋势铺垫
2. 文中至少一处具体数字，无"显著""大幅"
3. 至少一处诚实局限表达
4. 各节篇幅不均匀
5. 无"综上所述""赋能""打造"
6. 破折号未过度使用
7. 引号未过度使用
8. 正文无"朴素"

## §6 风格模式：JavaGuide AI 系列

**当用户指定 JavaGuide 模式时，应用本节全部规范。覆盖默认模式的对应条款。**

### 6.0 核心写作原则：理解后重新创作

**最高优先级规则。** 格式、结构、语气——一切规范在它面前都让路。

**正确的流程四步：**
1. **完整理解**：通读参考资料，直到能脱稿向同事讲清楚
2. **提取要素**：抓住核心观点、逻辑链条——不是抓原句
3. **忘掉原句**：合上参考资料。脑子里只剩"我想说什么"
4. **重新讲一遍**：用自己的语言写。像给朋友解释一样

**自检**：随便挑一段对照参考资料。句子层面找不到逐句对应关系但观点逻辑一致→过。能逐句对齐只是换了词→不过，重来。

**参考资料与版权边界：**

不算侵权：技术名词、代码示例/API调用/配置片段、官方定义原话引用（注明出处）、架构图/流程图结构、YAML/JSON固定格式

算侵权/洗稿：对概念的个人理解方式和解释路径、非官方的个人原创例子和场景、个人见解/评价/态度、行文节奏和叙述顺序、文章开头钩子和收尾

**核心判断**：技术事实只有一个，但**叙述方式可以不同**。先消化，再按规范写。

### 6.1 文章整体结构

```
YAML Frontmatter
→ 开头钩子（个人经历/痛点/真实场景，1-3段）
→ "这篇文章讲什么"导航列表（编号+字数）
→ 核心内容（## / ### 层级）
→ 自然收尾（可选，不需要单独的"总结"章节）
→ 参考资料列表（如有）
```

**YAML Frontmatter：**
```yaml
---
title: 文章标题（直击主题，可用冒号分隔，可用疑问句）
description: 一句话概述，含核心关键词，80-120字
category: AI 应用开发
head:
  - - meta
    - name: keywords
      content: 关键词1,关键词2,关键词3（5-10个）
---
```

**title 规范**：不要"详解""深入""一文搞懂"等修饰词。

**description 规范**：含核心关键词，概述覆盖的子主题。

**开头钩子** — AI 系列最鲜明的特征。实测概念系列 8 篇全部用故事/痛点/反直觉开场，0 篇用学术摘要。五种模式：

| 模式 | 说明 | 实测占比 |
|------|------|---------|
| A 个人经历/踩坑故事 | 最常用，自曝"我一开始也以为 X" | ~37%（概念系列） |
| B 常见误区/反直觉现象 | 纠正常见误解，"别只盯模型" | ~25% |
| C 读者常见困惑 | 代读者提问，列两种极端再给中间路线 | ~13% |
| D 行业观察/变化 | 从宏观切入 | ~13% |
| E 场景对话/剧本式 | 面试官/同事对话开场，戏剧感最强（如 llm-gateway 面试官对话） | 个别但效果最强 |

**误区破题是跨全部子系列的核心说理骨架**（实测概念 7/8、实战 practices 4/4）。第一句否定流行误解或自述踩坑，再翻转。模板：`很多人/我一开始以为 X，后来发现不是/根本不是这么回事，真正的问题是 Y`。

**导航列表（"阅读契约"仪式，概念系列 6/8 篇标配）**：在开头钩子之后、正文之前（第 3-5 段位置）固定放，是概念系列的签名仪式。实战系列通常没有这种"阅读契约"。
```markdown
这篇文章会把 XXX 拆开讲清楚。全文接近 7000 字，主要看这几块：
1. 要点一
2. 要点二
```
固定元素：字数提示（"接近 7000 字"）、长文加"建议收藏"（>5000字）、5-7 条导航要点。

**结尾模式（按子系列区分）**：
- **概念系列**：回扣开头的误区 + 给一条"先做 X，再做 Y"的最小可行落地路径。不是"总结本文讲了什么"。实例：context-engineering 结尾"先把 System Prompt 和工具边界写清楚；再把 RAG 检索做准"；rag-optimization 给 9 步落地优先级。
- **实战 cases**："写在最后" + 参考资料列表（官方文档链接）。
- **实战 practices**：总结段回扣核心理念，无"写在最后"，无参考资料。

### 6.2 语气与行文风格

**像一个有经验的开发者在跟你聊天**——有观点、不端着、敢说"我觉得"。

| 特征 | 说明 |
|------|------|
| 第一人称 | 用"我""我们""Guide" |
| 直接评价 | 不怕说某个东西不好 |
| 口语叙事 | 用讲故事方式解释技术 |
| 自曝踩坑 | 亲身经历增加可信度 |
| 读者对话 | 直接用"你"对话读者 |
| ai-coding 开场自称（按子系列分化） | **cases 系列**用"大家好，我是 Guide"/第三人称"Guide"/"笔者"（偏正式，建客观记录感）；**practices 系列**统一"你好，我是小 G"（4/4 篇，建个人权威感）。不是随机混用，自称分化是签名 |

**误区破题范式（最高频开篇法，跨全部子系列）：**

几乎每篇第一句否定一个流行误解或自述踩坑，再翻转。模板：
> 很多人/我一开始以为 X（朴素认知），后来发现不是/根本不是这么回事，真正的问题是 Y。

实例：
- 「做 LLM 应用时，我一开始也以为最麻烦的是模型接入。后来发现不是。」
- 「很多 AI 应用的第一个版本都很"顺"……但一上生产，麻烦马上变得具体」
- 「第一次做 RAG 时，很多人的体验都差不多：文档切了，向量库建了，Top-K 也调大了，模型还是一本正经地胡说八道」

不用"今天我们学 X"。先建立"你以为简单"再翻转，勾住读者。

**生活化比喻范式（概念系列讲解骨架，实战系列仅破题段偶用）：**

读者先通过比喻建立直觉，再读术语。**概念系列**密度高（每千字 1-2 个，几乎每节一个）；**实战系列**密度低（集中在开头概念祛魅段，正文实操段不用比喻，用截图和代码代替）。

**锚定比喻机制（概念系列核心）**：每个抽象概念配一个**会被后文反复回引的锚定比喻**，不是随机比喻。实例：
- MCP = "接线规范"（作者还会吐槽"AI 领域的 USB-C"这个比喻容易让人误会）
- Context Engineering = "给厨师准备厨房（食材放哪、刀具怎么摆）"
- Harness = "模型是 CPU，Harness 是操作系统"
- RAG = "证据加工流水线"；RAG vs 微调 = "随查随用 vs 把手册背下来"
- Progressive Disclosure = "查书/到新城市先给地图"
- 上下文窗口 = "工作台（不是垃圾桶）"

写比喻的标准：用读者已知的生活场景映射技术概念，让人先"懂个大概"再展开。比喻出现在三个位置：概念首次定义后、反直觉/难懂机理处、对比两个易混概念时。

**口语化词汇**（适度使用而非均匀分布）：放转折/降预期/预判疑问等功能位置，不随机撒。**按子系列分化（实测 15 篇扫描结果）**：

| 系列层 | 高频（≥4 篇） | 适中（2-3 篇） | 个别/低频 |
|--------|--------------|---------------|----------|
| 概念系列通用 | 说白了、坑/踩坑、别/不要、搞懂、其实、更稳的做法、一句话 | 翻车、扛住、够用 | 玄/很玄 |
| 实战系列真高频 | **干活/干起活来、兜底/兜得住、跑起来/跑得起来** | 翻车、劝退 | 真香、爆肝、屎山代码（各 1-2 次） |

**勘误提醒**：旧版词表的"一把梭、牛头不对马嘴、一本正经地胡说八道"在实战系列 7 篇扫描中 **0 次出现**，属臆造或概念系列误植，不要使用。实战系列口语化服务于"实操可信度"，偏向工程师行话（干活/翻车/兜底/跑起来），不是为了趣味性。

### 6.3 内容组织模式

**概念拆解型**（MCP/RAG/Agent Skills 等）：
```
是什么？→ 为什么需要？→ 和相近概念的边界 → 核心原理/架构 → 怎么落地
```

**系统工程/链路拆解型**（RAG 优化/AI 应用架构）：
```
问题场景 → 全景图(Mermaid) → 环节逐个拆解 → 排查路径
```

**实操指南型**（Spec Coding/Codex）：
```
开场故事 → 核心理念 → 对比 → 具体步骤 → 常见坑 → 工具清单
```

**面试题型**（AI 面试题系列）：
```
### ⭐️ 问题标题
简短回答 + 展开解释 + 代码/架构图补充
```

**实战案例型**（ai-coding/cases 系列，实测 cc-glm5.1/claude-desktop-cc-switch/deepseek-v4-claude-code）：
`
打招呼（大家好我是 Guide）+ 上下文承接 → 环境准备/安装配置（截图密集）→ 场景一/实战一（需求→AI分析→代码→效果验证）→ 场景二（同上）→ 实战总结（能力维度表+做得好/需注意+建议）→ 写在最后（强调人工评审）→ 参考资料（官方文档链接）
`
特征：场景驱动，每个场景是独立闭环，**每个场景有可量化的验收结果**（如"性能提升超过 60 倍"）。代码穿插在编码环节但前后必配口语说明。第一人称退到"笔者"或省略，建客观记录感。自称"Guide/笔者"。

**工具实践型**（ai-coding/practices 系列，实测 claude-md-best-practices/spec-coding/the-cool-tricks/claudecode-tips）：
`
打招呼（你好我是小 G）+ 读者反馈/催更/真香回忆 → 概念祛魅/误区破题 → 核心理念/四步法（分小节带代码块）→ 进阶：项目变大后怎么管 → 踩坑/失败模式清单 → 模板/命令/工作流清单 → 总结（回扣核心理念，无"写在最后"）
`
特征：建议清单驱动，按风险高低分层（小任务/中等任务/高风险任务）。截图用于配置步骤和读者互动。自称"小 G"。第一人称密度极高建个人权威感。

**实战系列三件套（practices 签名，必须）**：
1. **命令清单**：可复制命令分类列出（如 claudecode-tips"常用命令"分"会直接干活的/辅助的/治理的三类"）
2. **模板清单**：可直接用的 Spec/CLAUDE.md/配置模板（如 spec-coding 三套 Spec 模板）
3. **踩坑清单/失败模式表**：症状+处理方式两列表（如 claudecode-tips"常见失败模式表"）

**按风险/规模分层签名（practices 核心结构）**：几乎所有 practices 篇都有"什么场景用哪一层"的分层。实例：
- spec-coding 按"10 模块以内/10-30/30+"
- the-cool-tricks 按"贵模型 vs 便宜模型"分工
- claude-md-best-practices 按"CLAUDE.md vs rules vs Skills vs Hook"约束硬度

概念系列讲"是什么"，实战系列讲"什么场景用哪一层"。

**cases vs practices 内部差异总表**：

| 维度 | cases | practices |
|------|-------|-----------|
| 自称 | "Guide"/"笔者" | "我"/"小 G" |
| 钩子 | 场景导航 | 读者反馈+真香回忆 |
| 主力格式 | AI 对话截图+优化前后对比 | 命令清单+模板清单 |
| 表格类型 | 数据对比（参数/定价） | 概念辨析（X vs Y） |
| 第一人称密度 | 中（"笔者"） | 高（"我"） |
| 比喻密度 | 极低 | 偏低（集中在破题段） |
| 结尾 | "写在最后"+参考资料 | "总结"+回扣核心理念（无参考资料） |
| 时态 | 操作记录体（已完成） | 经验分享体（持续性） |

**一句话区分**：cases="我做了 X，结果 Y"的实战报告；practices="我建议你这样做 X"的经验手册。
### 6.4 格式元素规范

**代码块**：语言标注必填。AI 系列特有类型：`text`（Prompts）、`json`（API 响应）、`yaml`（配置）、`mermaid`（流程图）。

**源码/参数处理四原则（跨子系列统一约束）：**

1. **表格为默认论证载体，代码密度远低于表格。** 对比表/参数表/场景表三件套承担清单化呈现决策维度的工作。实例：llm-gateway 760 行 134 处表格行 vs 16 个代码块；rag-optimization 694 行 53 处表格行 vs 10 个代码块。
2. **代码只放带中文注释的关键片段，绝不裸贴大段实现。** 每个代码块前后必有口语解释——先说这段在干什么，贴代码，再说为什么这么写。实例：pgvector 查询带行内注释 `-- <=> 是余弦距离运算符(0 = 完全相同, 2 = 完全相反)`；structured-output 用「坏设计/好设计」成对片段而非完整类。
3. **大段实现源码放末尾独立章节，不在正文散落。** 实例：workflow-graph-loop 把完整 Spring AI Java 实现放进独立 `## 代码实现` 专节，按「第一步/第二步/第三步」分步骤组织，每步配中文说明。
4. **复杂逻辑用 Mermaid 流程图表达而非源码。** 实例：知识更新的「源系统→变更检测→队列→处理→去重→Embedding→三端写入」全链路用 Mermaid 而非代码。

**表格**：最常见三种——对比/差异表、层级/职责表、问题诊断表。首列加粗。

**Blockquote**：三种用途——官方文档引用（英文原文+中文翻译）、"说明一下"补充说明、扩展阅读/前置知识提示。

**Mermaid（系统工程/全链路拆解型专用，不是全系列通用）**：实测仅 rag-optimization 密集用（4 个 flowchart，有统一配色体系），其他概念篇 0-1 个，**实战系列 7 篇 0 个 Mermaid**（用 drawio/svg 图片代替）。`flowchart LR`（横向流程链路）或 `flowchart TB`（纵向层级递进）。配色（仅 Mermaid 场景适用）：client 青色、gateway 紫色、business 橙色、infra 紫色、storage 蓝色。节点统一 `rx:10,ry:10` 圆角矩形。

**配图三种方式（按子系列选择）**：
- 预制图（**docs/ai 概念系列主力**，实测 8/8 篇全用）：上传到 oss.javaguide.cn，正文用 ``![图名](https://oss.javaguide.cn/...)`` 引用 SVG/PNG。文件名英文短横线化、语义化、带主题前缀（如 ``mcp-four-layer-architecture.png``）。单篇常 8-15 张，agent 概念组几乎全用预制图不用 Mermaid。每 800-1200 字一张。
- Mermaid 代码图（**仅 RAG/系统工程全链路系列主力**，如 rag-optimization）：正文直接写 ```` ```mermaid ```` 围栏。配色固定复用（见上方）。
- 截图（**ai-coding 实战系列主力**，实测 7 篇平均 10+ 张）。五类用法：
  - **配置步骤截图**（cases 主力）：每步配置配截图，教程式
  - **AI 输出效果截图**（cases 主力）：证明 AI 真做到了
  - **读者互动截图**（**practices 签名社交证明**）：读者催更/评论/阅读量截图——spec-coding 贴读者催更、the-cool-tricks 贴读者评论、claudecode-tips 炫阅读量 6w+。**这是 practices 区别于 cases 和概念系列的关键签名**
  - **官方文档截图**（practices 主力）：贴 Claude Code/工具官方文档截图建权威性
  - **优化前后对比截图**（cases 主力）：如"18 秒 → 300ms"对比

**交叉引用**：织入正文叙述而非单独"相关阅读"区块。三种模式——正文中自然引出、前置知识条件、系列导航。

### 6.5 内容质量要求

- 标注时效：引用具体日期（"截至 2025-06-18"），不用"当前""最新"
- 量化工程感：拿具体数据说话，不泛泛说"性能更好"
- 观点有理由支撑
- 参考资料格式：官方文档放最前面，不放低质量转载

### 6.6 标题层级

- `##`：一级章节，`###`：二级章节，`####`：三级（极少用）
- 概念定义用疑问句、关系对比用疑问句、**过程/选择/方法类也用疑问句**（"stdio 和 Streamable HTTP 怎么选？""各范式怎么选？""怎么落地？"）。第三类实际文章里高频出现，不要只用陈述句。
- ⭐️ 标记（**可选，非通用**）：实测概念系列 8 篇仅 skills 1 篇用，实战系列 7 篇 0 次。仅用于超长文（>8000 字）且概念密度高的篇章，标注最核心 2-3 个章节引导读者优先阅读。不作通用要求
- 口语化句式贯穿标题：「到底」「到底有什么区别」「能不能」「是什么关系」可反复使用
- AI 系列**不使用**数字前缀（如 ``## 1 背景``）

## §7 工作流

### 7.1 模式判断
- 有素材原文 → 优化模式
- 无素材原文 → 创作模式

### 7.2 风格模式判断
- 提及 JavaGuide / javaguide / "按本项目的风格写作" → **JavaGuide 模式**，应用 §6
- 未指定 → **默认模式**

### 7.3 深度阅读素材

读取指定素材。提取核心观点、事实数据、方法链条、原文文体。

识别问题：是否缺细节、结构模板化、技术深度不足、文体错配。

### 7.4 知识补全

有信息缺口时搜索补充。补全只服务于文章，不塞无关背景。

### 7.5 目录确认

先输出粗目录，包含每节要解决的问题、计划补充的证据、优化模式下每节对应原文哪里。

### 7.6 创作/优化

创作模式：先选文体，再决定开头和结构。

优化模式：保留原文事实/数字/术语，优先重组骨架，把泛化改具体。

### 7.7 写入文件

优化模式：直接覆盖素材来源文件。
创作模式：询问用户指定路径。
