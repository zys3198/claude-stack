# Skill 留存判定 Rubric（强模型时代）

基准：JavaGuide《再见 Superpowers！很多 Skill 真的可以扔掉了》(2026-07-23) + 《Skill 的选择与精简》(2026-08-13，同作者演进版) + 本机 2026-07-23 精简审计先例。
用法：skill-trimmer 流程第 3 步逐个判定时对照本表。不逐字读——需要某条判据细节时按节查。

**两层来源，分开标**：`【文章】` = JavaGuide 文原意（2026-08-13 文新增判据已在相应节标注）；`【本机】` = 你 2026-07-23 审计先例 / memory，文章没有、后加的。冲突处在第四节「本机护栏」逐条标注张力。要纯文章激进版，忽略 `【本机】` 条目。

---

## 一、四问删减标准（文章的删减门槛）

每装/评一个 skill，问四句：

1. **这件事模型原本就会做吗？** —— 会 → 分两档：**Redundant**（本来就会、随时想起）→ 倾向删；**Activation**（知道但不会主动想起）→ 可留作提醒、描述收短。模型不知道 → **Expert** → 必须留。（三级明细见第七节）
2. **没有它时，我是否反复在同一个地方翻车？** —— 是 → 倾向留。
3. **它有没有沉淀脚本、模板、专业资料或个人偏好？** —— 有 → 倾向留。
4. **这套规则过期之后，我有没有办法发现并删掉？** —— 没有 → 标注待审。

一句话：**只会反复提醒「先读项目、再写代码、最后跑测试」的 skill，直接删。** 项目真有特殊要求，写进 CLAUDE.md/AGENTS.md 更省事。

### 装前评估（2026-08-13 文新增【文章】）

装新 skill 前，先「**不用它跑一次**」——能跑好就不装；同一个问题反复出现，才把那一小段流程留下来。再对照四问。**装前必看安全面**：至少读 SKILL.md + scripts/ + references/（SKILL.md 是给 Agent 的指令，藏危险命令/过宽权限会真被照做）。

### 维护量基线 <20（2026-08-13 文新增【文章】）

作者「经常使用、愿意长期维护的不到 20 个」。总量远超 20 且大量零使用 = 书签心态信号，push 整体收敛。

### 描述列表预算 ~2% / 8000 字符（2026-08-13 文新增【文章】）

渐进式披露下名称+描述常驻上下文，超限先缩短描述、再移除 skill。判定时优先「收窄描述」或「移除」而非在库里新增。

## 二、三类值得留（保留判据）

### A 类 · 偏好沉淀（模型猜不到的固定产物）
特征：文章风格、图表规范、公司/项目内部模板、特定代码库发布流程。
判据：没有它，每次交付风格会漂移；有了它，同一套标准能稳定复现。
例：draw.io 绘图 skill（固定图表样式+避开反复踩的排版坑）、ai-text-polisher（文风）、javaguide-style-guide。
本机对应：`learned/` 目录（ai-coding-coach 沉淀）、各 guide 的风格预设。

### B 类 · 专业判断 + 脚本/资料
特征：靠一句 prompt 覆盖不全的任务，skill 把「检查项 + 工具脚本 + 证据来源」打包，用到时再加载。
判据：有没有 scripts/ references/ assets/？有没有非平凡 checklist？有没有外部证据源？
例：安全审查、复杂文档处理（docx/pptx/xlsx）、特定框架迁移、生产检查、plagiarism-audit。
反面：纯文字「记得做 X 再做 Y」无资产 → 不是 B 类，滑向 D 类。

### C 类 · 方向纠错（防开工走错方向）
特征：不教模型怎么写代码，在开工前把含糊处问出来/把方向校准。
判据：它的存在是否改变了「什么时候开始动手」和「先做什么」？模型越强执行越快，走错方向代价越大——这类最难被强模型替代。
例：grill-me（一次一问追问需求）、expose-unknowns（开工判四象限）、to-prd。

### D 类 · 流程步骤型（默认候选删）【文章】
特征：操作清单——怎么读项目、怎么找调用链、改完跑哪些测试、提交前查什么。
判据：全是常规步骤、无项目特有约束、无脚本/模板/检查项 → 零增量信息，删。
注意：D 类里**被路由引用**或**弱模型兜底**的除外（见第四节，均为【本机】护栏，非文章原意）。

### 套件流程型 · 启用时机重审【文章·主论点】
特征：Superpowers 类大而全套件里的流程件（brainstorm / writing-plans / TDD / worktree / subagent 执行 / review / verify）。
判据（文章为什么「很少再用 Superpowers」）：
- 流程完整性 ≠ 价值——改一处校验逻辑就走完「需求澄清→设计→计划→执行→审查→验证」，时间被流程吃掉。
- 流程越完整，越考验**启用时机**；任务不够复杂时，它从保护变成负担。
- 非常烧 token。
判定动作：对套件里每个流程 skill，问「**启用时机写清了吗？小任务会不会被它拖着走全流程？**」时机模糊 → 列「过度流程候选」。
对照：文章作者现在偏爱 mattpocock/skills——小、可改、可组合、不接管整个开发过程，只取眼前需要那一块。
注意：本机护栏（第四节 #2）给流程型留了「弱模型兜底」后门，与本条张力见冲突 #2——判定时呈给用户权衡，不默认豁免。

## 三、归属分层（规则该放哪，别全塞 skill）

很多 skill 越写越大，是把所有规则都塞进了 SKILL.md。分层：

| 规则性质 | 该放哪 |
|----------|--------|
| 每轮任务都要遵守的项目约定 | CLAUDE.md / AGENTS.md / 项目规则文件 |
| 只在特定任务才需要的流程 | Skill |
| 耗时长、制造大量中间信息的支线调查 | Subagent |
| 要把 Skills/Hooks/MCP 统一分发给团队 | Plugin |
| 漏一次就出问题的机械约束 | Hook / CI / linter / 测试（不靠自然语言提醒） |

判定时的用法：一个 D 类 skill 里如果只有 1-2 条是真正项目特有的，正确动作是**把那 1-2 条挪进 CLAUDE.md，然后删 skill**，而不是留着整个 skill。

## 四、本机决议（【本机】，2026-07-25 用户拍板；覆盖文章通用判据）

> 以下 3 条曾是「文章 vs 本机」的张力点，2026-07-25 用户已拍板定案，不再是待权衡项——直接按决议判，不重新呈分歧。

1. **被 router 引用的 D 类 → 删 skill + 改路由。** 用户：「skill 没用的话肯定可以改路由啊。」
   - 动作：判 D 类且没用的 skill，即便被引用也进「移除+改路由」——移动后**必须同步修掉** router/CLAUDE.md/其他 skill 里的引用（用 guide-skill-auditor 或手动），不留死引用。引用扫描产出的就是这份「待修清单」。
   - （背景：2026-07-23 曾因删 `tdd`/`triage` 造成 router 死引用——所以现在删引用的 skill 必须连引用一起改，不是不能删。）
2. **流程型/E 类 → 留兜底。** 用户：「留兜底。」
   - 动作：流程型（含套件流程件）不一刀切删。只有「纯 D 类 AND 零引用 AND 无资产」才进移除候选；带「弱模型+复杂任务兜底」价值的流程型默认保留，标「保留-流程兜底」。
   - （与文章张力：文章主张强模型已会补流程、流程型该重审。本决议按用户「按任务分级用模型」留后门。）
3. **Superpowers 套件 → 不审。** 用户：「不审。」
   - 动作：整个 SP 套件豁免启用时机审查，不进「过度流程候选」，默认全留。文章的「套件流程重审」立场（见第三节）只对**非 SP** 套件或散装流程型 skill 生效。
4. **同能力多个 → 留 router 指定的主路径那个。** 重复的判定「哪个是主路径」，不是「哪个名字好听」。（与文章无冲突。）
5. **分类建议必须用户拍板。** AI 出表，用户逐项定，不自动执行移除。

## 五、为什么「大而全套件」要谨慎（背景，非判据）

- 渐进式披露：skill 名称+描述常驻上下文，占用有上限。装太多，列表被截断/缩短，该命中的没命中；描述写太宽，一个普通改动命中好几份，规则冲突时模型临时判断听谁的，跑偏难排查。
- 流程完整性 ≠ 价值：brainstorm→plan→TDD→worktree→subagent→review 全套对复杂/陌生/高风险改动有价值，但改一处校验逻辑就走全流程，时间被流程吃掉。流程越完整越考验启用时机。
- 安全：SKILL.md 是给 Agent 的指令，第三方 skill 藏危险命令/过宽权限，Agent 可能照做。装前至少读 SKILL.md + scripts/ + references/。

## 六、常见误判（别踩）

- 「这个 skill 写得真详细真好」→ 详细 ≠ 增量。详细的常规步骤清单仍是 D 类。
- 「万一以后用得上」→ 书签心态。半年没用 + D 类 = 删。
- 「它提到了很多最佳实践」→ 最佳实践若是模型已知常识，不算资产。
- 「删了怕找不到」→ 移动不是删除，`_weak-model-backup/` 可恢复；直管目录进 lab-area 备份。
- 「当时有用 = 现在有用」→ 能力会被模型升级 / 别的 skill 覆盖，按「生命周期/被覆盖」（第九节）复查，不凭历史印象留。
- 「提醒型 = 冗余」→ 区分：模型知道但**不会主动想起**的是 Activation，有提醒价值，别当 Redundant 一刀切删；会主动想起的才是 Redundant。
- 「写得真规范 = 能留」→ 工程完整 ≠ 有增量。frontmatter 规范、步骤齐全但内容 Redundant，仍删。

## 七、知识增量三级（【框架】，细化第一节第 1 问）

| 级 | 定义 | 判定动作 |
|----|------|---------|
| **Expert** | 模型（当前主力模型级）不知道的内容——领域专有知识、项目特有约束、稀缺脚本逻辑 | 必须留，对应 A/B/C 类 |
| **Activation** | 模型知道但不会主动想起——少见 flag、某框架版本坑、自己常忘的规范 | 可留作提醒；描述收短、少占路由；若只是「提醒一句」，优先并进 CLAUDE.md 或并入相关 skill，不单开 |
| **Redundant** | 模型本来就会、随时想起——常规步骤、通用最佳实践 | 删，对应 D 类 |

注意**模型相对性**：当前主力模型下是 Redundant 的，弱模型下可能还是 Expert。判定基准用「当前主力模型」，弱模型兜底走本机决议 #2。

## 八、工程体检清单（【框架】，每项不过即「需工程修复」）

1. **frontmatter 有效**：有 name + description？description 够短能路由、不空泛？（对照 SKILL.md 触发面维度，太宽就「收窄描述」）
2. **内容完整度**：任务步骤 / 输入输出说明 / 前置条件 / 错误处理——缺了标「需工程修复」。注意：完整 ≠ 免删，完整但 Redundant 仍删。
3. **安全面**：SKILL.md + scripts/ + references/ 有无危险命令、过宽权限、未授权的网络/文件操作？——SKILL.md 语义供应链攻击是真实研究领域（2026 论文），第三方 skill 必查。有 → 隔离 + 「删前用户确认」。
4. **依赖面**：移除它断不断别的 skill/router/CLAUDE.md 的引用？——断 → 列引用方清单，走「移除+改路由」或「需工程修复（补依赖）」。
5. 深度内容评分（SkillLens 9 维）交 darwin-skill；本清单是轻量门槛。

## 九、生命周期 / 被覆盖退役（【框架】+ SLIM）

skill 不是静态资产：装时有用，模型升级 / 他 skill 覆盖后价值归零。SLIM 方法（arXiv《Dynamic Skill Lifecycle Management for Agentic RL》）的「按贡献动态退役」本机落点：

- **退休判据**：
  a. 模型能力提升后已能覆盖 → Expert 降 Redundant → 「移除-被覆盖」。
  b. 其他 skill 已覆盖同能力 → 留 router 主路径那个（本机决议 #4），余者「移除-被覆盖」。
  c. 反复翻车的场景另有兜底（CLAUDE.md 规则 / hook / 别的 skill）→ 冗余。
- **创建触发（SLIM 反向）**：审计中发现「某失败场景反复出现、无任何 skill/规则兜底」→ 值得新建 skill（走 skill-creator）。这是审计的增值输出，不止删。
- **状态标注**：报告给每个候选标 active / stale / archived（映射见 SKILL.md「数据驱动」节）。

## 十、数据驱动：轻量证据信号（【框架】）

无遥测基建，不假装有数据。判「使用面」时只列可核信号：

- **mtime / git log**：文件多久没动（半年未动 + 零引用 + D 类 → stale）。
- **引用方**：router 还引用吗？memory 还有提及吗？（引用方清单即改路由清单，见 SKILL.md 流程第 2 步）
- **installing/ 台账**：装于何时，之后有无使用记录。
- **用户实测**：同任务「开/关该 skill」各跑一次 = 穷人版 A/B，不搭评测集。

判定动作：信号齐了才下「删」建议；信号缺失 → 标「数据缺失」，不硬猜。正式 A/B 评测（skill-up，`github.com/alibaba/skill-up`）需评测集，当前不建，记为演进方向。
