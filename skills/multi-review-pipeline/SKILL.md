# Multi-Review Pipeline

对 Markdown 文档执行多维度并行审查。调用方式：`/multi-review-pipeline <文件路径>`

## 执行步骤

### Step 1: 确认文档与语言

1. 确认目标文件路径存在且为文本文件
2. 检测文档语言（中/英），审查输出匹配文档语言
3. 如文件过大（>500 行），先分段并告知用户

**失败处理**：
- 文件不存在 → 报错退出，告知用户路径错误
- 非文本文件（二进制/图片）→ 报错退出，列出支持的格式
- 文件 > 1000 行 → 分段审查，告知用户"将分 N 段审查"

### 🔴 STOP — Step 1 完成检查

文件存在且为可审文本？
- ✅ → 继续 Step 2
- ❌ → 已在上方处理，不继续

### Step 2: 派发并行审查 Agent

使用 `Agent` 工具派发独立子 agent，每个读全文，产出结构化发现列表。

**每个 Agent 输出格式**：
```
[严重程度] 行 Lxx: 问题描述 → 建议修正
```

严重程度：`critical` / `minor` / `suggestion`

**固定 4 个 Agent 角色与职责**：

| # | 角色 | 审查重点 |
|---|------|---------|
| 1 | Factual Accuracy Checker | 技术声明有据可查、版本号/API签名准确、代码示例可运行、外部引用有效 |
| 2 | Style & Voice Critic | AI文本特征检测、语气一致性、中英文混排规范、可读性 |
| 3 | Structure & Flow Analyzer | 标题层级、段落衔接、交叉引用、信息密度均衡 |
| 4 | Technical Depth Reviewer | 受众匹配度、关键细节遗漏、边界情况覆盖、安全/性能隐患 |

**条件性第 5 个 Agent：Plagiarism Auditor（有外部来源时触发）**

判定条件：用户在本轮调用时**提供了外部来源**——消息里含 URL（`http`），或"来源""参考""对照""原文""依据""as 原文"等词 + 来源路径/粘贴文本。文章自带参考链接（如文末"参考资料"列官方文档）不算触发来源。

触发后：调用 `plagiarism-audit` skill。按其工作流——多路抓取来源、提取每来源原创元素清单、派评判员逐句对照、区分技术事实（允许）vs 原创措辞搬运（必改）、多轮复判至 PASS。该 agent 的发现按 `critical`（逐字抄袭）和 `minor`（高仿/同义改写）计入。

无外部来源时跳过，保持原 4 agent。

**派发参数**：`subagent_type: "general-purpose"`，每个 agent 的 prompt 包含完整文档路径 + 角色职责 + 输出格式要求。

**失败处理**：
- Agent 超时（>60s）→ 该维度标记"未完成"，其余继续
- Agent 返回空结果 → 记录"该维度未发现问题"，不阻塞
- 4 个 Agent 全部失败 → 报错退出，提示用户重试

### Step 3: 合成去重

1. 收集全部 Agent 的发现列表
2. 去重：同一行同一问题多次报告 → 合并为一条，标注来源（如"[Agent1+Agent4]"）
3. 按严重程度排序：critical → minor → suggestion

### 🔴 STOP — 展示修订清单，等用户确认

向用户展示完整修订清单，含行号、问题描述、建议修正。
**不执行任何修改**，等用户说"执行"/"OK"/"改吧"。

### Step 4: 执行修正

| 严重程度 | 处理方式 |
|---------|---------|
| critical | 自动应用（仅限单行/短语修正），大段重写仍需确认 |
| minor | 逐项展示，等用户确认 |
| suggestion | 仅列出，不自动修改 |

**失败处理**：
- 修改冲突（两个 critical 改同一行）→ 暂停，展示冲突让用户选择
- 修改后文件语法错误 → 回滚该修改，告知用户

### Step 5: 输出报告

输出以下内容：

```
📊 审查报告
- 总发现数：[N]
- 去重后：[N]
- 已修改（critical）：[N]
- 待确认（minor）：[N]
- 仅建议（suggestion）：[N]

各维度评分（1-5）：
  事实准确性：[N]  风格语气：[N]  结构流程：[N]  技术深度：[N]

修改 diff：
[git diff 输出]
```

## 不要做什么（反例清单）

| # | 反模式 | 正确做法 |
|---|--------|---------|
| 1 | 不确认直接修改原文 | Step 3 后必须等用户确认再执行 |
| 2 | 跳过去重直接应用 | 同一问题多 Agent 报告必须合并，避免重复修改 |
| 3 | 审查二进制/图片文件 | Step 1 报错退出 |
| 4 | 单个 Agent 失败就中止 | 标记该维度"未完成"，其余继续 |
| 5 | 对 suggestion 级别自动修改 | suggestion 只列出，用户说改才改 |
| 6 | 不输出 diff 只说"改完了" | Step 5 必须包含 diff 统计 |
| 7 | 混淆本 skill 与 tech-article-review | 本 skill 是多 Agent 并行+批量修改；tech-article-review 是单次增量评审 |
