# AI Product Development

本 skill 仅在用户显式调用 `/ai-product-development-by-user` 时执行。模型不得基于上下文、关键词或任务类型自行调用。

把开发者时间从盯代码，转向想清楚产品、划定边界和验证结果。先确认产品流程，再让 Agent 执行；基础功能跑通后，再选择合适的协作入口持续跟进。

## 工作流程

### 1. 明确产品意图

先回答：

- 谁会使用？
- 他们要完成什么？
- 为什么现在需要它？
- 首版做到什么程度算够？

产出一句产品定义和一条核心用户路径。信息缺口会改变结果时才提问。

### 2. 用 AI 反复打磨原型

在写代码前，用 AI 设计工具迭代原型：

- 验证核心流程是否走得通；
- 展示关键页面和状态；
- 覆盖成功、失败、空状态和权限交互；
- 删除无法支撑核心路径的页面和功能；
- 先定视觉方向：检索参考图 → 让用户挑选 → 生成多套方向稿，再用选中的方向约束后续实现。

原型阶段有两个独立目标：确认产品怎么用，以及确定视觉方向。前者靠流程和状态覆盖达成；后者在原型阶段一并定下，跳过它直接进入实现，产出容易显得廉价，靠功能验证补不回来。

### 3. 划定 MVP

将需求分成三组：

- **必须有**：完成核心路径不可缺少的能力；
- **可以后做**：不影响首版验证的增强项；
- **明确不做**：本轮禁止扩大的范围。

为每项必须有的能力写验收标准。优先保证一条完整可用路径，不追求功能数量。

### 4. 把原型和需求交给 Coding Agent

任务说明至少包含：

- 产品背景和目标用户；
- 当前原型或流程材料；
- MVP 范围与明确不做事项；
- 验收标准；
- 技术和环境约束；
- 完成后需要汇报的改动、验证结果和阻塞点。

一次只交付一个可验收结果。需求不清时，Agent 先提问，不自行扩大范围。

原型优先交付带交互的 HTML：它比静态设计稿多一层可运行结构，比成品代码少一层耦合，作为交接格式既能让 Agent 看到真实交互，又不把它绑在实现细节上。

### 5. 先跑通基础功能

先实现核心路径并实际运行，再处理边缘体验：

1. Agent 执行一个小任务；
2. 查看运行结果，而不是只看代码；
3. 对照验收标准判断完成度；
4. 记录问题，形成下一条任务。

Agent 报告“完成”不等于功能完成，必须有可运行结果或可核对证据。

### 6. 可选的异步跟进

基础功能稳定后，再支持离开电脑时的协作：

- 发起开发任务；
- 回答 Agent 的澄清问题；
- 处理权限和关键决策；
- 查看日志、截图、演示或测试结果；
- 决定下一轮任务。

手机只是其中一种协作入口。异步跟进不改变 MVP 边界，也不替代最终验证。

### 7. 持续小步迭代

每轮只推进一个明确结果：

```text
反馈 → 下一条任务 → Agent 执行 → 实际验证 → 决定继续或调整范围
```

若反馈改变产品方向，先更新核心路径和 MVP 边界，再继续编码。

## 每轮产出

完整启动时整理：

1. 产品定义；
2. 核心用户路径；
3. MVP 清单和不做清单；
4. Agent 任务说明；
5. 验收标准；
6. 当前结果、阻塞点和下一条任务。

用户只要求其中一个阶段时，只产出该阶段内容，不强行展开完整流程。

## 约束

- 不跳过原型验证，直接把模糊想法交给 Agent；
- 不把非 MVP 功能混入当前任务；
- 不把原型当成已验证的生产实现；
- 不把异步或移动入口设为产品开发的前置依赖；
- 不用 Agent 的自我描述代替运行结果；
- 遇到阻塞时说明已知事实、缺失信息和待决策项。

## 完成判断

同时满足以下条件才算本轮完成：

- 核心路径可以实际运行；
- 验收标准逐项有结果；
- 结果可在当前工作环境或异步入口查看；
- 下一轮任务边界明确。
