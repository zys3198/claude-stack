# Model-agnostic parallel delegation

把判断、架构、取舍和最终验收留给主代理；把范围清楚、结果可验证的执行交给 worker。

## Route

1. 先判断子任务是否独立、边界是否清楚、结果是否可单独验收，以及并行收益是否超过协调成本。
2. 准备派发时读取 [`dispatch-contract.md`](dispatch-contract.md)。只读且范围不重叠、宿主明确支持并发的任务可并行；有依赖或冲突风险时分阶段或顺序执行。
3. 批量并行（≥2 个 worker）前先派一个 worker 单跑同类任务，核对路由、权限、输入契约和产物格式；单跑未验证可靠不得放并行——首次暴露的通常是脚本和配置问题（参数传错、prompt 漏条件、权限少一项），单步不可靠就并行只会同时收到一堆看不懂的改动。
4. 涉及模型、effort、并发、隔离能力、失败或子代理配置选择时，读取 [`runtime-and-failure.md`](runtime-and-failure.md)。需要选择或调整配置时，先向用户说明配置是否合理及原因，再询问是否采用；未确认前不启动 worker。
5. 整合前读取 [`verification.md`](verification.md)，按风险完成主代理复核和最终报告。

## Keep in main agent

需求理解、整体架构、跨任务取舍、强耦合修改、权限与安全判断、外部或不可逆动作、最终整合、最终答复。

## Non-negotiable boundaries

- worker 只能执行收到的唯一子目标，不重定义总目标、不扩大范围、不创建下级 worker。
- 只读任务可在不重叠范围且宿主明确支持并发时并行；写任务必须使用宿主提供的隔离，或明确不重叠文件范围。共享文件、生成物或状态存在冲突风险时顺序执行。
- 生产操作、外部发送、删除、迁移和权限变化遵守宿主确认门禁，不能用并行绕过。
- worker 返回“完成”不等于验收完成；主代理必须检查实际结果、diff、文件范围和检查输出。
- 只交计划不算完成。blocked/failed 不算完成；不得把推测、默认路由或未观测的模型写成事实。

## Runtime policy

运行时允许时，低风险且边界清楚的任务优先使用较低 effort；跨文件推理、高风险或复杂取舍再提升。任意模型均可参与，只要宿主实际暴露对应调度、隔离和验证能力；不按供应商、模型名或固定档位筛选，不写死字段名。

## Configuration gate

准备选择或调整子代理配置时，必须先向用户明确展示：拟选模型（可见时写实际名称）、provider、route、effort、并发数和隔离方式；判断配置是否合理，说明原因、影响和备选方案；询问用户是否采用。未获确认前不得启动 worker；不依赖配置回答的分析可以继续。宿主未暴露的值写 `unverified`，已确认同一配置时不重复询问。

## Scope discipline

不要为一次委派自动修改全局配置、项目规则或持久化角色定义。任务完成后只报告实际派发、实际路由、实际检查、整合结果和剩余风险；无法验证的值明确标记 `unverified`。
