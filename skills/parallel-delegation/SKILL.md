# Model-agnostic parallel delegation

把“判断”留给主代理，把边界清楚、结果可验收的“执行”交给 worker。模型、供应商、推理档位和并发上限都来自当前运行时或用户明确配置，不写死名称，也不把配置文件内容当成运行时证据。

## 1. 先判定是否值得并行

适合委派的子任务同时满足：

- 输入范围清楚；
- 不依赖其他子任务的中间结果；
- 输出可以单独验收；
- 能指定文件、目录、符号或资料边界；
- 并行收益大于协调成本。

保持在主代理中的任务：需求澄清、整体架构、跨任务取舍、强耦合修改、最终整合、最终答复，以及一次性小改动。

读操作可在不重叠范围内并行。写操作只能使用宿主提供的隔离 worktree，或明确不重叠的文件范围；没有隔离且存在写冲突风险时顺序执行。生产操作、外部发送、删除、迁移和权限变化不得因并行而绕过确认门禁。

## 2. 主代理先拆解，再调度

主代理在派发前确定：

1. 总目标和不变约束；
2. 每个 worker 的唯一子目标；
3. 输入与允许读取范围；
4. 输出格式；
5. 验收条件；
6. 禁止触碰的文件、系统或操作；
7. 是否读操作、写操作、是否需要隔离；
8. 可用的模型、推理档位和并发限制。

每个 handoff 使用以下最小契约：

```text
Task: <唯一子任务>
Scope: <允许读取和修改的范围>
Inputs: <已知上下文、文件、约束>
Output: <必须返回的结果>
Acceptance: <主代理可执行的验收条件>
Boundaries: <禁止修改、禁止外部操作、禁止继续委派>
Isolation: <read-only | isolated-write | disjoint-write>
```

不要用模糊指令“看看这个项目”替代范围和验收条件。不要让 worker 重新定义总目标或整体架构。

## 3. 模型和运行时规则

- 用户明确指定模型或推理档位时，按用户指定值调用；先确认宿主支持。
- 用户未指定时，可为边界清楚的执行任务选择当前运行时可用的合适 worker 模型；成本不是唯一标准，任务难度和验证能力优先。
- 只使用运行时实际暴露的模型、推理参数、并发和隔离选项；不猜模型 ID、字段名或调用语法。
- 不修改主会话模型，不设置全局默认 worker，不创建供应商专属配置来伪造通用能力。
- 若宿主不支持模型覆盖，使用宿主实际提供的 worker 路由；若无法确认实际模型或路由，明确报告“未验证”，不得声称使用了某个模型，也不得静默降级。
- 并发上限以运行时实际限制为准。不要为了制造进度条提高并发数。

## 4. Worker 行为边界

Worker 只完成收到的子任务：

- 不创建下级 worker；
- 不改变整体架构或扩大范围；
- 不修改无关文件；
- 不执行破坏性操作、外部写操作或提交/推送；
- 不把推测写成已验证事实；
- 发现范围、权限或运行时能力不满足时停止并报告。

Worker 返回以下结果，不只返回“完成”：

```text
Status: completed | blocked | failed
Result: <实际结果>
Files inspected: <实际检查文件>
Files changed: <实际修改文件，无则写 none>
Checks: <实际运行的检查及结果>
Blockers: <阻塞，无则写 none>
Risks: <剩余风险，无则写 none>
Runtime: <宿主实际暴露的 worker/model/effort；无法确认则写 unverified>
```

## 5. 主代理验收和整合

主代理等待所有已派发 worker 返回，再逐项处理：

1. 检查状态是否 completed；blocked/failed 不算完成；
2. 对照 handoff 的 scope 和 acceptance 检查结果；
3. 检查实际 diff、文件范围和测试输出；
4. 发现越界、缺证据或失败时拒绝结果，必要时缩小任务后重新派发；
5. 按依赖顺序整合隔离 worktree 或不重叠修改；
6. 运行整体检查，确认子任务组合后仍满足总目标；
7. 最终答复区分已验证、未验证、阻塞和未运行。

不要因为 worker 返回“完成”就跳过主代理审查。只有运行时证据能确认模型/effort/路由时，才在结果中写具体值。

## 6. 失败和降级

- 子任务边界不清：回到主代理澄清或缩小范围，不盲目派发。
- 任务存在顺序依赖：改为阶段式调度，后一阶段等待前一阶段验收。
- 文件范围重叠：拆分边界、启用隔离，或顺序执行。
- 模型覆盖不支持：保留任务契约，使用已验证的宿主默认路由；不能确认时停下报告。
- 并行启动失败：不要伪造并行结果，改为顺序执行或报告阻塞。
- 部分 worker 失败：保留成功结果但不宣布总任务完成，先处理失败项和整体检查。

不要为一次任务自动创建或更新全局配置、项目规则文件或持久化角色定义；只有用户明确要求固化工作流时才单独处理，并先展示影响范围。

## Final report

完成后简要报告：总任务、实际派发的 worker、并行/顺序原因、每个 worker 的状态和实际检查、已验证的运行时路由、整合结果、剩余风险。不要把未验证的模型或并发值写成事实。
